## 왜 Rate Limit 이 필요한가?

레이트 리미터는 정해진 시간 동안 한도를 넘는 요청을 막아 트래픽 속도를 조절하게 해준다.

- 스트리밍 플랫폼(Soop, Chzzk)에서 한 명의 사용자가 초당 10개의 채팅을 친다면?
- GPU 처리 플랫폼에 CLI 로 한 명의 사용자가 초당 5건씩 요청 한다면?
- 해커가 무차별 대입 공격으로 초당 10만건의 공격을 한다면?

이외에도 다양한 경우에도 사용할 수 있다.

## 알고리즘

### 고정 윈도우(Fixed Windows)

정해진 시간 구간 안에서 정해진 횟수만 허용한다.

- 요청마다 카운터가 1씩 오른다.
- 새 윈도우가 시작되면 0으로 돌아간다.
- TTL 은 고정으로, 지나면 자동으로 사라진다.

![image](https://assets.youngsu5582.today/blog/2026/11/10/1794315928993-image.png)

- 장점 : 구현과 이해가 쉬움, 사용자가 예측하기 쉬움
- 단점 : 윈도우 끝 무렵에 요청을 시작하면, 한도의 2배까지 처리를 한다 - `2x burst`

> Github API 는 시계 기준 매 정시 리셋되는 고정 윈도우를 쓴다고 한다.

24시간 윈도우라면, 시간대 문제를 고려해야 한다.

- 하루 단위 제한을 `자정`에 리셋하면, 서버 시간 & UTC 기준시, 다른 시간대 사용자는 새 날인데 제한이 안 풀려 당황할 수 있다.
- 사용자 시간대 기준으로 바꾸면 악용이 될 수 있다. (2x burst)

=> 다른 방법을 사용하는게 더 좋다.

### 슬라이딩 윈도우(Sliding Windows)

용량을 다 채우는 대신, 한 요청씩 차례로 회복한다.

- 허용된 요청의 시각을 기록
- 새 요청이 오면, 지금 이 순간 기준 범위내 구간만 본다. (이전 구간은 자동 삭제)
- 한도에 도달한 상태에서 새 요청이 오면 거절

![image](https://assets.youngsu5582.today/blog/2026/11/10/1794316448117-image.png)

- 장점 : 트래픽이 고르게 분산된다. 고부하 환경에 적합
- 단점 : 고정 윈도우보다 예측 어려움. 요청마다 타임스탬프 저장해야 해서 자원이 많이 듦

> 고트래픽용 알고리즘이 자원을 많이 먹는건 모순이다.
> Cloudflare 같은 서비스는 근사치를 사용한다. - Floating Window
> 근사값 = (이전 윈도우 카운트 × 이전 윈도우 가중치) + 현재 윈도우 카운트

### 토큰 버킷

토큰이 일정한 속도로 채워지고, 요청 하나가 토큰 하나를 꺼내 쓴다.

![image](https://assets.youngsu5582.today/blog/2026/11/10/1794316707012-image.png)

- 장점 : 순간적 폭주는 허용하나, 장기적 평균은 지켜짐. 허용 범위 안 트래픽 급증에 유연
- 단점 : 고정 윈도우보다 한도와 리필 시점을 사용자에게 설명하기 어려움

> Stripe : 버킷 용량 500, 0.01초마다 토큰 1개 리필

### 동시 실행 제한

Concurrency limit
현재 동시에 처리 중인 작업 수를 제한한다.

- 작업을 시작할 때 슬롯을 하나 차지한다.
- 작업이 끝나면 슬롯을 반환한다.
- 사용 가능한 슬롯이 없다면 새 요청 거절하거나 대기시킨다.

- 장점 : 오래 걸리는 작업이 한꺼번에 몰려, 서버 자원 고갈되는 것을 방지한다.
- 단점 : 작업이 끝났을 때 슬롯 정상적 반환하지 못하면, 실제 처리 중인 작업이 없어도 새로운 요청이 막힌다.

슬롯 반납이 보고에 의존한다.

- 서버가 처리 도중 죽음
- 네트워크 끊겨 완료 신호 유실
- 예외 처리에서 반납 코드 빠뜨림

-> 카운터가 내려가지 않고, 슬롯만 꽉찬 상태가 될 수 있다!
=> 슬롯에 만료 시간을 걸거나, 반드시 보장하는 코드로 구성

### GCRA

Generic Cell Rate Algorithm
토큰 버킷과 결과는 똑같으나, 토큰 개수가 아닌 `다음 요청이 허용되는 시각` 만 저장하는 방식

- 요청이 들어오면 저장된 기준 시각 확인
- 현재 시각과 허용된 버스트 범위를 기준으로 요청 허용할지 판단
  - 요청을 허용하면 기준 시각을 요청 간격만큼 미래로 이동
  - 요청을 거절하면 기준 시각을 변경하지 않고, 언제 다시 요청할 지 계산

- 장점 : 사용자당 숫자 하나만 저장. 토큰 다시 채우는 계산 필요 X
- 단점 : 토큰이 줄고, 차는게 아닌 미래 시각을 미리 당겨쓰는 방식. 직관적 X

## 그 외 고려할 점

### 저장소를 영속화

서버를 늘리거나, 재시작하거나 서버리스라면 메모리에 두면 안된다.
-> Redis 같은 공유 메모리 저장소를 사용하자.
=> 최적화가 필요하다면, 앞단에 메모리 캐시를 두어 막혀 있는 사용자는 Redis 까지 가지 않고 차단할 수 있다.

###Fail open

저장소 연결이 끊겨도, 서비스 전체를 막으면 안된다. (부가 서비스가 흐름 차단)
-> 모든 요청을 허용하자.

### 키를 잘 고르자.

이 키를 기반으로, 사용자의 흐름을 제어한다.
잘못 설정한다면, 정상적 사용자도 에러를 마주칠 수 있다.

추가로, 공격을 막기 위해선 어느것도 완벽하다고는 할 수 없다.

- 일반적으로 사용하는 사용자 ID
-> 한명의 사용자가 여러 사용자 ID 를 사용해서 요청

- API 라면, API 키 기준
-> 위와 동일한 문제, API Key Rotation

- 로그인 하지 않은 사용자는 IP, 기기 식별자 등
-> IP 는 VPN 및 고정 지울수 없다. 여러 기기 사용
