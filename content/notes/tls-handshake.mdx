Transport Layer Security

데이터를 안전하게 주고받는 프로토콜

- 기밀성 : 중간에서 엿봐도 내용을 알 수 없다
- 무결성 : 중간에서 대응을 바꾸면 받는 쪽이 알아챈다
- 인증 : 상대가 진짜 그 서버인지 확인한다

HTTPS 는 HTTP 를 TLS 위에서 보내는 것이다. - `TCP -> TLS -> HTTP`

`Handshake` 와 `데이터 전송` 두 단계로 동작한다.

## Handshake

![image](https://assets.youngsu5582.today/obsidian/2026/11/23/3f80d628d4ad88a95459d8ee09b8babd.png)


### 1. ClientHello

- 지원 버전 : 쓸 수 있는 TLS 버전
- 암호 방식 목록 : 데이터를 암호화할 알고리즘 후보
- 서명 방식 : 서버 서명을 검증할 수 있는 방식
- 키 교환 그룹 : 키 교환에 쓸 수 있는 수학 방식
- 서버 이름 : SNI, 접속하려는 도메인
- 클라이언트 난수
- 키 교환 공개값

1-RTT 를 위해서 미리 키 재료를 첫 메시지에 넣는다.
평문으로 전송한다.

### 2. ServerHello

- 고른 버전 : 이번 연결에 쓴 TLS 버전
- 고른 암호 방식 : 클라이언트 목록 중 하나
- 서버 난수
- 키 교환 공개값

서버는 클라이언트가 제출한 후보중 고른다.
서버가 ServerHello 를 보낸 순간 키를 계산할 재료를 다 가진다.

=> 바로 다음 메시지부터 암호화한다.

### 같은 비밀 키 계산

양쪽이 각자 하는 계산이다.
서로 공개값을 주고 받고, 같은 비밀을 만든다!

=> Diffie-Hellman, 디퍼 헬만 알고리즘 기반이다.

#### 디퍼 헬만 알고리즘

- 간단한 예시

> p = 23, g = 5 라는 공개 약속으로 시작 (공개 되어있음)

|             | 클라이언트                    | 서버                       |
| ----------- | ------------------------ | ------------------------ |
| 비밀값 (안 보냄)  | a = 6                    | b = 15                   |
| 공개값 (보냄)    | A = 5⁶ mod 23 = **8**    | B = 5¹⁵ mod 23 = **19**  |
| 받은 공개값으로 계산 | B^a = 19⁶ mod 23 = **2** | A^b = 8¹⁵ mod 23 = **2** |

외부로 `23, 5, 8, 19`가 노출이 되지만
`6, 15` 라는 값을 알지 못하면 2라는 값에 도출할 수가 없다.

이 알고리즘으로 같은 키는 얻지만, 아직 상대가 누군지 & 믿을수 있는지 모른다.

### 3. Certificate

서버가 클라이언트에게 자신을 인증하기 위해 보낸다.

- 암호화해서 전달 (TLS 1.2 에서는 평문)
- 크기가 크다 : 인증서 한 장 1~2KB, 묶음은 수 KB
	- TLS 레코드 여러 개, TCP 패킷 여러 개로 나뉘어 올 수 있음

인증서 체인을 전달한다.

#### 인증서 체인

서버 인증서 ← 중간 CA 인증서 ← 루트 CA 인증서

- 서버 인증서 : 도메인 이름, 서버 공개키, 유효기간, 발급자, 발급자 서명
- 중간 CA 인증서 : 서버 인증서에 서명한 기관의 인증서
- 루트 CA 인증서 : 보통 보내지 않고, 클라이언트가 이미 가지고 있음

클라이언트는 이 정보를 기반으로

- 서명을 따라 올라가면 내가 믿는 루트 CA 에 도달하는지
- 인증서 안의 도메인 이름이 내가 접속한 이름이 맞는지
- 유효기간 안인지 & 폐기되지 않았는지

인증서는 공개 문서이다 -> 이 메시지만으로는 `이 서버의 진짜 주인` 임이 증명되지 않는다!!

### 4. CertificateVerify

서버가 클라이언트에게 보낸 인증서의 주인이 자기라는걸 증명하기 위해 보낸다.

- 암호화해서 전달
- 크기는 수백 바이트 이하

서버가 `인증서의 개인키`로 지금까지 주고받은 메시지 전체의 해시값에 서명한다.
클라이언트는 인증서 안의 공개키로 서명을 검증한다.

-> 복사한 인증서로는 이 서명을 만들수가 없다. (개인키가 있어야만 가능)

> 인증서 키는 서명에만, 데이터 암호화는 디퍼 헬만 알고리즘을 통한 키 교환으로

### 5. Finished

서버가 클라이언트에게 지금까지 대화가 조작되지 않았다고 알려준다.

- 암호화해서 전달
- 크기는 32~48 바이트(해시 길이)

대화 기록을 Hashing 후, 키 교환으로 만든 키로 HMAC 해서 전달한다.
-> 값이 같으면, 양쪽이 같은 키로 게산했고 중간에 아무도 대화를 바꾸지 않았다는 증명

서버 Finished 직후, 대화 기록을 섞어 `데이터 전송 키`를 뽑는다.

이후 클라이언트는 3~5를 검증하고 자기 Finished 를 보내며, Handshake 가 끝이 난다.
-> 이제부터 `데이터 전송 키`로 암호화한다.

## 데이터 전송

Handshake 가 끝나면, HTTP 요청 & 응답을 암호화해서 주고받는다.

![image](https://assets.youngsu5582.today/obsidian/2026/11/24/6d0dac2d84f75296c6430023ea678c27.png)

### 1. 자르기

HTTP 바이트를 최대 16KB 조각으로 자른다.

#### 자르는 이유

인증 태그가 끝에 붙어 있다.
받는 쪽은 레코드를 통째로 다 받아야 검증하고 풀 수 있다.
-> 조각이 크면 그만큼 오래 기다리고, 그만큼 많이 쌓아 둬야 한다.

- 메모리 상한 : 레코드 하나당 최대 16KB 만 모으면 된다. 파일의 크기는 상관없다
- 빠른 송/수신 : 응답 전체 기다리지 않고, 생기는 대로 보내고 받는 쪽도 앞부분부터 해제
- 변조 검증 : 레코드마다 따로 검증하므로 조작된 레코드를 바로 검사 가능

### 2. 암호화

조각마다 따로 암호화한다.

- 순서 번호 : 레코드마다 번호를 넣고, 암호화에 섞는다
- AEAD(?) : 암호화와 인증 태그 계산을 한 번에 하는 방식

### 3. 레코드

| 부분 | 크기 | 내용 |
|---|---|---|
| 헤더 | 5 B | 레코드 종류, 길이 |
| 암호문 | 최대 16 KB | 잘린 HTTP 바이트를 암호화한 것 |
| 인증 태그 | 16 B | 이 레코드가 안 바뀌었다는 확인값 |

레코드 당 추가되는 양 자체는 21B 정도로 매우 작음

### 4. TCP 전송

레코드를 TCP 로 보낸다.
레코드 하나가 패킷 여러 개로 나뉘어 오기도 하고, 패킷 하나에 레코드 여러 개가 같이 오기도 한다.

### 5. 모으기

받는 쪽은 레코드 하나가 다 도착할 때까지 받은 조각을 모아 둔다.

- 헤더의 길이 값을 기반으로 레코드가 다 왔는지 확인
- 인증 태그는 맨 마지막에 존재 -> 전체가 와야 검증 가능

![image](https://assets.youngsu5582.today/obsidian/2026/11/24/14d90fc814d775cebed514ff474b1e63.png)

### 6. 검증 & 복호화

인증 태그가 맞다면, 복호화해서 평문 조각을 꺼내고 응답을 바이트로 이어 붙인다.
틀리면, 평문을 꺼내지 않고 연결을 끊는다.
