Why -> What -> how -> Opinion

주장을 구조화를 하자.

## 왜 기술은 아는데, 설득이 어려울까?

아는 것을 논리적 순서로 꺼내는 훈련이 없었기 때문이다.

### ❌

- 기술적 솔루션부터 말한다
-> Redis 캐시 쓰면 됩니다.

=> 왜 필요한지 설명 없이 결론만 던진다.

- How 만 지나치게 강조한다
-> 기술 스택만 나열한다.

=> "그래서 뭘 원한 건데?"

- 논리적 결론, 향후 방향성이 없다
-> 어떻게 했습니다.

=> 판단과 결론이 없다.

내용은 있지만 구조가 없다.

## W2HO

### Why

> 문제와 배경, 왜 이것이 문제인가?

배경과 맥락을 제시한다. 먼저 공감을 시킨다.

Why 를 제시하는 순간,
청중은 그 문제를 스스로 떠올리게 된다.
공감이 생긴 상태에서 What 을 들으면 저항 없이 수용한다.

> 대화는 설득이 아니라 공감이다.
> '이 문제 나도 겪었는데?', '문제가 있네?' 와 같은 문제 인식이 선행되어야 모든 말이 설득력을 가진다.

- 문제제기

```
장애 발생 시 평균 4시간 서비스가 중단됩니다.
그때마다 고객 문의가 폭주하고 팀 전체가 멈춥니다.
```

- 파급 효과

```
실제로 고객 이탈이 발생했고, 팀 신뢰도도 바닥을 쳤습니다.
```

- 배경(트렌드 및 환경 변화)

```
클라우드,AI 전환이 가속화되면서 기존 온프레미스 중심 아키텍처로는 변화를 따라가기 어려웠습니다.
```

### What

> 개념과 해결책, 무엇이 필요한가?

해결책의 개념과 방향성을 제시한다.

Why 에서 만든 공감 위 `이런 것이 필요하다` 는 방향성을 놓는다.
단, 아직 구체적 방법을 말하진 않는다.

- 해결책
- 목표
- 개념

```
마이크로서비스 아키텍처로 전환이 필요합니다.
```

```
DevOps 파이프라인 도입을 통해 해결할 수 있다.
```

### How

> 기술, 방법, 도구: 어떻게 구현하는가?

구체적 기술,방법,도구들을 청준 수준에 맞게 조절해서 말한다.

- 기술
- 방법
- 단계

```
도메인 경계를 정의하고, API Gateway 를 앞단에 두며,
서비스별 독립 배포 파이프라인을 구현했습니다.
```

> 청준이 실무진 및 리더면 How 를 깊게, 임원진이면 What 까지만 하자

### Opinion

> 판단, 결론, 방향, 내 판단은 무엇인가?

How 에서 멈추면 단순 보고서가 된다. (대부분의 개발자가 How 까지만 말한다.)

결론,권고,향후 방향을 말한다.

- 결론 &  권고

```
MSA 전환을 권고드립니다.
단, 도메인 경계 설정을 먼저 충분히 검토하지 않으면 분산 모놀리스가 될 위험이 있습니다.

첫 6개월은 핵심 도메인 2개만 분리하는 점진적 전환을 제안합니다.
```

- 트레이드오프 인식

```
초기 비용은 높지만, 장기적으로 유지보수 비용이 낮아집니다.
```

- 향후방향

```
다음 단계로 서비스 메시 도입을 검토할 수 있습니다.
```

- 교훈 & 반성

```
이 경험으로 배운 점은 초기 설계 결정의 중요성입니다.
```

## 이 구조가 통하는 심리적 이유

WHY 를 제시하면?
-> "맞아. 나도 그 문제 겪었어." 가 떠오른다. - `공감 형성`

WHAT 을 그 다음 제시하면?
-> "아, 그 문제를 이렇게 해결하는구나" 라고 생각한다. - `저항 없는 수용`

HOW 를 제시하면?
-> "구체적으로 어떻게 구현되는지 알겠다." - `신뢰 구축`

OPINION 을 마지막으로 제시해
-> "이 사람은 확실히 본인의 의견과 향후 방향이 있는 사람이다." - `전문가 인상`

=> 인간은 Why가 해결되지 않으면 다음 내용을 받아들이지 않는다.
설득 기술이 아닌 인간의 인지 흐름에 맞춘것이다.

### 같은 구조, 다른 깊이

- 상위 의사결정자라면? (대표이사, 임원)

Why와 What 까지만 깊게 다루자.
How 는 한 줄 요약으로 충분하다.
Opinion 에서 비즈니스 임팩트를 강조하자.

- 실무 책임자라면? (팀장, 아키텍트, 기술리더)

How 를 충분히 깊게 다루자.
기술적 근거와 트레이드오프를 포함하자.
Opinion 은 기술적 판단과 향후 방향으로 마무리하자.

- 엘리베이터 스피치라면?

> 엘리베이터 스피치 : 엘리베이터를 타고 이동하는 매우 짧은 시간(보통 30초~1분) 동안 상대방에게 자신의 아이디어, 제품, 서비스 또는 자기소개를 핵심만 간결하고 강렬하게 전달하는 설득 기법

Why (1문장) -> What(1문장) -> Opinion(1문장) 으로 구성하자.
원한다면, How 를 얘기하게 빼두자.

### 예시

```
저는 MSA 프로젝트를 해봤는데요,
Docker랑 Kubernetes를 쓰고 API Gateway 도 넣었어요.
서비스를 8개로 나눴고, 각각 독립 배포했습니다.
JWT 인증도 붙이고 RabbitMQ도 써봤습니다.
그래서 배포 시간이 줄었습니다.
```

기술 나열에 그치고, 왜 했는지, 어떤 판단을 했는지가 없다!!!

### 개선

```
[Why] 모놀리식 구조로 배포 주기가 3개월, 장애 시 전체가 다운되는 문제가 있었습니다.
[What] 서비스 경계를 기준으로 MSA로 전환하기로 했습니다.
[How] 도메인 분석으로 8개 서비스로 분리, API Gateway 와 이벤트 기반 통신(RabbitMQ)을 적용했습니다.
[Opinion] 배포 주기가 2주로 단축됐습니다. 다만 분산 트랜잭션 처리가 새로운 복잡도로 남아 있어, 다음 프로젝트에서는 도메인 경계를 더 신중하게 정의하겠습니다.
```

-> 문제 인식 -> 판단 -> 실행 -> 반성까지.
조리있게 설명하는 전문가처럼 들린다.

## 하나의 프레임워크, 모든 상황에 적용

- 기술 면접

설계 경험, 트러블 슈팅, 기술 선택 이유등 모든 답변에 적용 가능하다.

```
Why(문제) -> What(선택) -> How(구현) -> Opinion(교훈)
```

- 임원 보고

Why+What 만 깊게, How 는 요약, Opinion 으로 의사결정 유도

```
문제 -> 해결방향 -> 비용/일정요약 -> 권고안
```

- 엘리베이터 스피치

30초 안에 설득을 해야 한다. 각 단계 한 문장 압축

```
Why(1문장) -> What(1문장) -> Opinion(1문장)
```

- 기술 발표 및 컨퍼런스

왜 이 기술을 선택했는지, 어떻게 적용했는지, 무엇을 배웠는지

```
문제제기 -> 접근법 -> 구현 -> 회고 & 교훈
```

- 기술 문서 및 RFC

아키텍처, 제안서, ADR 등등
왜 이 결정을 내렸는지가 중요하고 기록해야한다.

```
Context(Why) -> Decision(What) -> Implementation(How) -> Consequences(Opinion)
```

## 실무 체크리스트

- Why로 시작하고 있는가?
-> 결론이나 How 를 먼저 꺼내진 않았는가?

- Why에 구체적인 근거(수치, 사례)가 있는가?
-> "문제가 있었습니다"가 아니라, "X라는 수치로 증명됩니다"

- What과 How를 구분하고 있는가?
-> 개념(What)과 구현(How)을 섞어서 말하지 않는가?

- 청중에 맞게 How의 깊이를 조절했는가?

- Opinion으로 끝맺고 있는가?
-> How에서 끝나는 보고서가 아닌, 내 판단이 담긴 커뮤니케이션인가

### 연습 방법

의식적으로 해야한다.

1. 지난 프로젝트 회고 : 자신의 프로젝트 경험을 `Why->What->How->Opinion` 으로 2분 안에 정리해보기
2. 기술 블로그 글쓰기 : 트러블슈팅 글을 이 구조로 작성해 글쓰기/말하기를 동시에 훈련해보기
3. 오늘 회의에서 바로 적용 : 다음 팀 회의에서 의견을 낼 때 Why부터 시작해보기

---

되게 좋은 말하기 방향성인거 같다.
물론, 익숙하진 않지만 좋은 말하기라고 어렴풋이 느끼고 있었던 거 같다.

이유를 말하고 -> 어떻게 했는지를 말하고 그 다음 흐름을 이끌어나가는 것이다.
어떻게 했는지까지 말하면, 상대방이 궁금해서 질문하든 & 내가 대답을 계속하든 2가지 중 하나가 가능하기 때문이다.

EX) 결제 크레딧 구현

- Why : 무료 크레딧으로 인한 운영 부담. 결제 흐름 로직을 담당하는 타팀과 개발 협의를 해야했습니다.
- What : 결제 크레딧 데이터 모델링과, HTTP API 와 비동기로 결제 크레딧 요청 처리를 설계했습니다.
- How
  - 충전, 차감, 재충전을 변경 기록으로, 크레딧 사용을 사용 이력으로 Append-Only 로 쌓고, 5년치 데이터를 조회하지 않게 잔액은 매번 갱신하는 구조로 설계했습니다.
  - 데이터 주권을 고려해 외부 서비스 콜백 결과에 상관없이 데이터를 반영하고, 콜백 실패시 재시도하는 스케줄러를 구현했습니다.
- Opinion : 최근 2개월 기준 전체 크레딧 사용의 약 6%를 유료 크레딧이 차지하고 있습니다. 그리고, Append-Only 로 쌓고 3개 테이블로 분리해 둔 덕분에, 사용한 크레딧을 전액 환불해야 한다는 회계 요구사항도 기존 데이터 구조사항 변경 없이 기록 추가와 데이터 보정만으로 처리할 수 있었습니다.
