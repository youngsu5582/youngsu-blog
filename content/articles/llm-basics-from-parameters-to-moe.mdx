> "GPT가 똑똑하다면서, 실체가 뭔데?" 라고 생각한 적 있다면, 이 글은 그 질문에 대한 답이다.

## 들어가며

ChatGPT, Claude, Gemini. 이제 일상에서 AI를 안 써본 개발자가 없을 것이다.
"코드 짜줘", "이 버그 잡아줘", "이 API 스펙 정리해줘" — 놀라울 정도로 잘한다.

근데 **실체가 뭘까?** 어떻게 숫자 덩어리가 코딩도 하고, 한국어 문맥도 파악하고, 농담도 하는 걸까?

이 글에서는 LLM(대형 언어 모델)의 기초를 하나씩 뜯어본다.
최신 모델의 기법(Mixture of Experts)까지, 왜 "저렴하게 잘 만드는" 모델들이 등장하는지 흐름을 따라가보자.

---

## 1. 파라미터 — AI의 뇌 크기

LLM의 핵심은 **파라미터(Parameter)**다. 파라미터는 신경망을 구성하는 **가중치(Weight) 숫자** 하나하나를 말한다.

비유하자면, 파라미터는 **뇌의 시냅스 연결 강도**와 같다.

- 파라미터가 많을수록 → 더 복잡한 패턴을 기억하고 더 정교한 추론 가능
- 대신 더 많은 메모리와 연산이 필요

### 실제로 얼마나 되나?

| 모델 | 파라미터 수 | 비고 |
|---|---|---|
| GPT-3 | 1,750억 (175B) | 2020년, LLM 시대의 시작 |
| Llama 3.1 70B | 700억 (70B) | 오픈 모델, 실무에서 널리 쓰임 |
| Llama 3.1 405B | 4,050억 (405B) | Meta, 오픈 공개 최대급 |
| GPT-4 (추정) | ~1~1.8조 | 비공개, 추정치 |
| 최신 대형 MoE 모델들 | 1조+ | MoE 구조 (뒤에서 설명) |

> 💡 GPT-4, Claude, Gemini는 정확한 파라미터 수를 공개하지 않는다. 업계 추정치만 존재한다.

### 파라미터 하나가 하는 일

LLM 내부는 거대한 **행렬 곱셈**의 연속이다. 입력 텍스트가 숫자 벡터로 변환되고, 파라미터 행렬과 곱해져서 출력이 나온다.

```
입력: "나는 오늘 _____"

1) 단어를 숫자 벡터로 변환 (임베딩)
   "나는" → [0.23, -0.87, 0.41, ...]
   "오늘" → [0.12, 0.55, -0.33, ...]

2) 파라미터(가중치 행렬)와 곱하기
   입력 벡터 × 가중치 행렬 = 출력 벡터

3) 출력을 다음 단어 확률로 변환
   "행복하다" → 72%
   "슬프다"   → 5%
   "피자"     → 1%

→ "나는 오늘 행복하다" 라고 생성!
```

이때 가중치 행렬 안의 숫자들(`0.71`, `-0.22`, `0.89`...)이 바로 **파라미터**다.
학습 전에는 전부 랜덤값이지만, 학습을 거치면서 "한국어 문법", "Java 코드 패턴", "논리적 추론" 같은 것들을 암묵적으로 인코딩하게 된다.

## 2. 모델 크기와 메모리 — RAM vs VRAM

파라미터가 많으면 모델 파일이 커지고, 그만큼 메모리가 필요하다.

### RAM과 VRAM의 차이

- **RAM (메인 메모리)**: 컴퓨터가 일반 작업에 쓰는 기억 공간. 브라우저, IDE, 슬랙을 띄울 때 쓰는 것.
- **VRAM (비디오 메모리)**: GPU 전용 메모리. AI 모델을 돌릴 때, 여기에 파라미터를 올려야 한다.

비유하자면:

> RAM = 책상 (넓게 쓰는 공간)
> VRAM = 실험대 (정밀한 작업 전용 공간)
> LLM을 돌린다 = 실험대 위에서 작업한다 = VRAM이 핵심

맥북의 경우 RAM과 VRAM이 통합(Unified Memory)되어 있어서, 64GB 모델이면 AI 실험용으로도 꽤 쓸만하다.

### 파라미터 수에 따른 모델 크기

| 정밀도 | 파라미터 1개당 크기 | 175B 모델 | 1.6T 모델 |
|---|---|---|---|
| FP32 (32비트) | 4바이트 | ~700 GB | ~6.4 TB |
| FP16 (16비트) | 2바이트 | ~350 GB | ~3.2 TB |
| INT4 (4비트 양자화) | 0.5바이트 | ~88 GB | ~800 GB |

RTX 4090 (VRAM 24GB)으로는 175B 모델조차 FP16으로는 못 올린다. 이것이 AI에 비싼 GPU가 필요한 이유다.

## 3. 숫자를 줄이는 기술 — FP32, FP16, 양자화

그렇다면 숫자를 **덜 정밀하게** 저장하면 메모리를 절약할 수 있지 않을까? 이게 바로 **양자화(Quantization)**의 핵심 아이디어다.

FP = Floating Point (소수점). 비유하자면:

- **FP32**: 원주율을 `3.14159265358979323846...` 까지 적음 → 정밀하지만 용량 큼
- **FP16**: 원주율을 `3.14159...` 까지만 적음 → 적당히 정밀, 절반 용량
- **FP8**: `3.14...` → 대충, 1/4 용량
- **INT4**: `3.1` → 근사치, 1/8 용량

| 정밀도 | 정확도 | 용량 | 속도 |
|---|---|---|---|
| FP32 | 가장 정확 | 4배 큼 | 느림 |
| FP16 | 충분히 정확 | 2배 | 빠름 |
| FP8 | 약간 손실 | 작음 | 더 빠름 |
| INT4 | 눈에 띄는 손실 | 가장 작음 | 가장 빠름 |

**핵심:** LLM에서는 FP32까지 갈 필요가 없다. FP16이나 FP8로 줄여도 성능은 거의 안 떨어지는데, 메모리는 반~1/4로 줄어든다. 그래서 실제 서비스에서는 대부분 FP16 이하로 모델을 돌린다.

## 4. 효율의 극대화 — Mixture of Experts (MoE)

여기까지 읽었으면 하나의 의문이 들 것이다.

> "파라미터가 1조 개면 VRAM이 수 TB인데... 어떻게 실제로 돌리는 거지?"

이 문제를 해결하는 핵심 기술이 **Mixture of Experts (MoE)**다.

### 핵심 아이디어: 모든 질문에 모든 뇌를 쓰지 말자

**일반 모델 (Dense):**

```
질문: "서울 날씨 어때?"
→ 1.6조 파라미터 전부 동원
→ 날씨 질문에 시(詩) 잘 쓰는 부분까지 굴림
→ 비효율적
```

**MoE 모델:**

```
질문: "서울 날씨 어때?"
→ Router가 이 질문을 분석
→ "이건 날씨/지식 관련이네. Expert #3, #7, #12 활성화!"
→ 1.6조 중 ~2000억 정도만 동원
→ 나머지 1.4조는 놀고 있음
```

비유하자면:

> 병원에 내과·외과·정형외과·피부과 의사가 100명 있다.
> - **일반 모델**: 환자가 오면 100명 전원이 다 같이 진료한다
> - **MoE**: 필요한 의사 5~10명만 진료한다

### MoE가 가져온 변화

MoE 구조 덕분에:

- 🟢 **속도 향상** — 적은 파라미터만 연산하니까
- 🟢 **GPU 메모리 절약** — 한 번에 쓰는 양이 적음
- 🟢 **더 큰 모델 구축 가능** — 전체 파라미터는 크되 실제 사용은 적게
- 🔴 **저장용 메모리는 여전히 필요** — 전체 모델은 크니까

이것이 최근 "1조 파라미터 이상" 모델들이 등장할 수 있는 기술적 배경이다.
전체는 거대하게 만들되, MoE로 효율적으로 사용하는 방식. 학습비를 획기적으로 낮추면서도 성능은 유지하는 핵심 기법이다.

## 5. 어떻게 "잘"하게 되나 — 학습 파이프라인

숫자 덩어리가 어떻게 코딩도 하고 한국어도 잘하게 되는 걸까? 3단계 파이프라인을 거친다.

### 1단계: 프리트레인 (Pre-training) — 세상 지식 주입

인터넷 전체 텍스트를 주입한다. 위키백과, GitHub 코드, 뉴스, 블로그, 책, 논문, StackOverflow...
그리고 **"다음 단어 맞추기"**만 수조 번 반복한다.

```
"오늘 날씨가" → 다음 단어? → "좋다" (정답!) → 파라미터 보상
"오늘 날씨가" → 다음 단어? → "포켓몬" (오답) → 파라미터 벌점
```

이 과정에서 모델은 한국어 문법, 코드 패턴, 논리적 추론 등을 **암묵적으로 학습**한다.
"이해"라기보다 **"패턴 암기"**에 가깝지만, 패턴이 워낙 방대하니 이해처럼 보이는 것이다.

### 2단계: 파인튜닝 (Fine-tuning) — 원하는 형식으로

프리트레인만 하면 질문에 엉뚱한 대답을 한다. 그래서 질문-답변 쌍으로 추가 학습:

```
Q: "Spring Boot에서 CORS 설정하는 법 알려줘"
A: "@Configuration 클래스에서 WebMvcConfigurer를 구현해서..."
```

이렇게 하면 "질문이 오면 이런 형식으로 답해야지"를 학습한다.

### 3단계: RLHF (인간 피드백 강화학습) — 취향 맞추기

여기가 진짜 마법이다. 모델이 답변 2개를 생성하면, **사람 평가자**가 더 나은 답변을 고른다.

```
A: "CORS는 Cross-Origin Resource Sharing의 약자입니다.
    Spring Boot에서는 다음과 같이 설정할 수 있습니다:
    @Configuration
    public class WebConfig implements WebMvcConfigurer { ... }"

B: "cors 설정하려면 WebMvcConfigurer 쓰셈 ㅋㅋ"
```

A가 더 낫다고 판단 → 모델이 A 스타일을 선호하게 학습.
이 과정에서 모델은 친절하게 답하기, 실행 가능한 코드 작성하기, 위험한 답변 피하기 등을 배운다.

## 6. 정리 — 숫자 1.6조 개의 창발성

지금까지 살펴본 흐름을 정리하면:

1. **파라미터** = AI의 뇌를 구성하는 숫자들. 많을수록 복잡한 패턴 학습 가능
2. **VRAM** = 이 숫자들을 올려놓는 공간. 파라미터가 많으면 더 큰 GPU가 필요
3. **양자화(FP16/INT4)** = 숫자의 정밀도를 줄여서 메모리 절약
4. **MoE** = 전체는 크게 만들되, 상황에 맞는 일부만 사용하는 효율적 구조
5. **학습 파이프라인** = 프리트레인(지식) → 파인튜닝(형식) → RLHF(취향)

개별 파라미터는 의미 없는 숫자 하나다.
하지만 충분히 많이 모이면 **갑자기** 추론, 코딩, 창작 같은 능력이 튀어나온다.
이 현상을 **창발성(Emergence)**이라고 부른다.

> 마치 물 분자 H₂O 하나하나는 "젖은 느낌"이 없는데, 10²³개 모이면 "물"이 되는 것처럼.

"진짜 이해"인지 "고도의 패턴 매칭"인지는 철학자들이 아직도 싸우는 문제다.
확실한 건 — 이 숫자 덩어리들이 우리 일을 돕고 있고, 앞으로도 더 도울 것이라는 점이다.
