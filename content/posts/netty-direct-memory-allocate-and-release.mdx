> Reactor-Netty 를 쓰는 서버 로직에서 Direct memory 관련 장애를 겪었다.
> 장애에 대해 제대로 이해하기 위해 개념부터 정리했다. 장애 이야기는 2편에서 다룬다.

이 글은 힙 밖 메모리(네이티브 메모리)가 어떻게 잡히고, 어떻게 풀리고,
Netty 가 그 위에 어떤 풀을 얹는지 순서대로 따라간다.

환경은 다음과 같다.

```text
Netty         4.1.135.Final
Reactor Netty 1.2.18
Reactor Core  3.7.19
JDK           21 (실험은 21.0.6)
```

### 3줄 요약

1. Direct 버퍼의 데이터는 힙 밖에 있고, JDK 는 이 용량을 힙과 별개의 한도(`MaxDirectMemorySize`)로 센다. 해제는 GC 가 `DirectByteBuffer` 객체를 발견해야 일어난다.
2. Netty 는 이 비용을 피하려고 큰 청크(chunk)를 한 번 받아 두고 잘게 나눠 쓴다. 버퍼는 `release()` 로 풀에 돌아가지만, 청크가 해제되는 것은 조건이 맞을 때뿐이다.
3. 한도에는 버퍼가 아니라 청크 단위로 잡히므로, 남은 한도가 청크 하나보다 작으면 새 청크가 필요한 할당은 아주 작은 버퍼라도 실패한다.

이번 편은 개념과 작은 실험까지다. 실험 코드는 [netty-core-playground](https://github.com/youngsu5582/playground/tree/ad54a706aa11ac9851520c7d2f7ed5d855947cd9/netty-core-playground) 에 있다.

## 네이티브 메모리와 Direct Buffer

네이티브 메모리는 JVM 프로세스가 운영체제로부터 할당받은 메모리 중 힙 메모리 영역을 제외한 영역이다.
여기에는 다음 요소들이 포함되어 있다.

- Direct Buffer 의 데이터
- Metaspace
- JIT 컴파일된 코드가 저장되는 영역
- JVM 내부와 Native 라이브러리가 쓰는 메모리

이번 내용은 Direct Buffer 에 대해 자세히 설명한다.

`ByteBuffer` 는 바이트 데이터를 담아 두고 읽고 쓰는 버퍼를 추상화한 클래스다.
두 가지 방식으로 만든다.

| 호출                          | 메모리      | 이름           |
| --------------------------- | -------- | ------------ |
| `ByteBuffer.allocate`       | JVM 힙    | HeapBuffer   |
| `ByteBuffer.allocateDirect` | 네이티브 메모리 | DirectBuffer |

`allocateDirect` 의 `DirectByteBuffer(int cap)` 생성자는 크게 네 단계 흐름으로 이루어져 있다.

```java
Bits.reserveMemory(size, cap);
…
    base = UNSAFE.allocateMemory(size);
…
UNSAFE.setMemory(base, size, (byte) 0);
…
    cleaner = Cleaner.create(this, new Deallocator(base, size, cap));
```

1. 한도에 할당 받을 메모리 먼저 예약
2. 네이티브 메모리를 받는다.
	- 실패하면 `Bits.unreserveMemory` 로 예약을 되돌림
3. 받은 메모리를 0 으로 초기화
4. 해제를 맡을 `Cleaner` 를 등록한다.
	- GC 는 힙 밖 메모리를 직접 수거하지 않음 → 객체가 수거될 때 해제하도록 걸어 둠

> JDK 21.0.6 `DirectByteBuffer.java` 생성자

`DirectByteBuffer` 객체는 힙에 있고 데이터는 힙 밖에 있다.
-> 힙 쪽 객체는 수십 바이트, Direct 버퍼를 많이 만들고 버려도 힙은 거의 차지 않고 GC 가 돌 이유가 거의 없음
=> Direct 는 할당에 할 일이 많고, 해제는 힙 쪽 객체가 정리되는 시점에 매달려 있다.

## Direct 메모리를 쓰는 이유

Direct 메모리를 쓰는 이유는 I/O 때 줄어드는 복사 때문이다.

>  DMA : Direct Memory Access, 메모리 직접 접근

- 힙 버퍼(`allocate`)로 read

1. JVM 이 `read` 시스템 콜을 호출하고, 커널 모드로 전환
2. 커널이 디스크에 읽기 요청, 요청한 스레드는 블로킹
3. DMA 로 데이터가 커널 버퍼에 복사
4. 커널이 커널 버퍼의 데이터를 임시 Direct 버퍼로 복사
5. `read` 가 반환되고 사용자 모드로 전환
6. JDK 가 임시 Direct 버퍼의 데이터를 힙 버퍼로 한 번 더 복사

- Direct 버퍼(`allocateDirect`)로 read

1. JVM 이 `read` 시스템 콜을 호출하고 커널 모드로 전환
2. 커널이 디스크에 읽기 요청, 요청한 스레드는 블로킹
3. DMA 로 데이터가 커널 버퍼에 복사
4. 커널이 커널 버퍼의 데이터를 Direct 버퍼로 복사
5. `read` 가 반환되고 사용자 모드로 전환 — 끝

DMA 로 인해 3번에는 CPU 가 관여하지 않고, 4번 · 6번 복사에는 CPU 가 관여한다.

“Direct Buffer 는 커널 버퍼를 직접 참조하니까 복사가 없는 것 아닌가?”
->  ❌ Direct 버퍼는 커널 버퍼가 아닌 힙 밖의 사용자 영역 메모리라서, 4번 복사는 모두 남는다.
=> Direct 가 줄이는 것은 `"6. 임시 Direct 버퍼 → 힙 버퍼"` 복사 한 번이다.

> 커널 쪽 복사까지 없애는 것은 `mmap` · `sendfile`(`FileChannel.transferTo`) 같은 다른 수단

> 그렇다고 Direct 가 항상 빠른 것은 아니다.
> 복사는 줄지만, 앞에서 본 생성자의 네 단계 때문에 할당과 해제는 힙보다 무겁다.

## JDK 의 할당과 해제

![image](https://assets.youngsu5582.today/obsidian/2026/11/26/93b196cb5f51f369fc1387180325ac7b.png)

### 한도

JDK 는 Direct 버퍼의 용량을 힙과 따로 더해 두고, 합계가 한도(`-XX:MaxDirectMemorySize`)를 넘는 할당을 거절한다.
옵션을 주지 않으면 한도는 최대 힙 크기와 같다.

#### 한도에 닿으면

한도에 닿아도 곧바로 실패하지 않는다.

```java
// 1
refprocActive = jlra.waitForReferenceProcessing();
…
// 2
System.gc();                                         
…
// 3
Thread.sleep(sleepTime);                             
sleepTime <<= 1;
…
// 4
throw new OutOfMemoryError                           
    ("Cannot reserve "
     + size + " bytes of direct buffer memory (allocated: "
     + RESERVED_MEMORY.get() + ", limit: " + MAX_MEMORY +")");
```

> JDK 21.0.6 `java.nio.Bits.reserveMemory` 메소드

1. 해제를 기다리는 버퍼가 있으면 그 정리를 기다리며 다시 시도
2. `System.gc()` 를 한 번 호출
3. 1 · 2 · 4 … 256 ms 씩 최대 9번(합 약 0.5초) 쉬며 다시 시도
4. 그래도 안 되면 `OutOfMemoryError: Cannot reserve N bytes of direct buffer memory` OOM 발생

=> 한도에 닿은 할당은 포기하기까지 약 0.5초를, 메모리를 요청한 스레드에서 기다린다.

### 해제

해제는 생성할 때 등록한 `Cleaner` 가 맡는다.

```java
private record Deallocator(long address, long size, int capacity) implements Runnable {
    …
    public void run() {
	    // 힙 밖 메모리 해제
        UNSAFE.freeMemory(address);              
        // 한도에서 뺀다
        Bits.unreserveMemory(size, capacity);    
    }
}
```

- `DirectByteBuffer` 객체에 참조가 없어지고
- GC 가 그 객체를 수거해야

`Cleaner` 가 실행되고 힙 밖 메모리가 해제된다.

=> Direct 메모리는 GC 가 돌아야 돌아온다. 힙이 한가하면 GC 가 늦게 돌고, 힙 밖 메모리는 그대로 남는다.

## Netty

Netty 는 네트워크 입출력을 적은 수의 스레드로 처리하고, 그때 쓰는 버퍼를 관리한다.
위에는 Reactor Netty(HTTP 클라이언트 · 연결 풀)가, 아래에는 JDK 와 OS 가 있다.

![image](https://assets.youngsu5582.today/obsidian/2026/11/26/dd51bf632d46b67b0b5cab1b522cdf0c.png)

### Selector, EventLoop

NIO 는 논블로킹 `Channel`, `Selector` 를 함께 써서, 스레드 하나가 여러 연결의 I/O 준비 상태를 관리한다. 연결마다 `read()` 를 부르고 기다리는 대신, 읽거나 쓸 수 있는 연결만 골라 처리한다.

- 연결당 필요한 플랫폼 스레드 수가 줄어든다
- 스레드별 스택 메모리와 컨텍스트 스위칭 부담이 줄어든다

`EventLoop` 는 이 구조를 감싼 것이다. 스레드 하나가 셀렉터와 작업 큐를 들고 다음을 반복한다.

1. 데이터가 생긴 연결이 있는지 묻는다 (`select`)
2. 그 연결을 읽고 파이프라인에 이벤트를 전달한다
3. 다른 스레드가 맡긴 작업을 처리한다

=> EventLoop 하나가 여러 연결을 맡으므로, 한 연결 처리가 오래 걸리면 다른 연결도 같이 밀린다.
(블로킹 주의!)

### Channel · Pipeline

- `Channel` 은 연결 하나고, 한 EventLoop 에 등록되고 이후 항상 그 스레드에서 실행된다.
- `Pipeline` 은 `Channel` 마다 하나씩 있는 핸들러 줄이다
	- 들어오는 이벤트는 앞에서 뒤로, 나가는 동작은 뒤에서 앞으로 흐른다.

```text
…
   91 ms | nioEventLoopGroup-2-1    | H1 channelRegistered
   91 ms | nioEventLoopGroup-2-1    | H1 channelActive
   96 ms | nioEventLoopGroup-2-1    | H1 channelRead  (데이터가 들어왔다)
…
```

### ByteBuf, Pool

`ByteBuf` 는 Netty 의 버퍼다.

Netty 는 소켓에서 읽을 때마다, 데이터가 있는지 알기 전에 버퍼부터 잡는다.
=> 읽을 때마다 할당이 일어나므로 할당이 부하를 주면 안 된다.

그런데 Direct 버퍼를 읽을 때마다 새로 만들면 두 가지가 문제다.

1. 만들 때 할 일이 많다 (한도 예약 · 네이티브 할당 · 0 채우기 · Cleaner 등록)
   → 읽을 때마다 이 비용을 낸다
2. 버릴 때 GC 를 기다려야 한다
   → 다 쓴 버퍼도 GC 전까지 한도를 차지한다

그래서 Netty 는 풀을 쓴다. 큰 덩어리(청크)를 한 번 받아 두고, `ByteBuf` 마다 그 안의 구간을 잘라 준다.

1. 무거운 Direct 할당은 청크를 받을 때만 치른다
2. 다 쓴 `ByteBuf` 는 GC 를 기다리지 않고 `release()` 로 바로 풀에 돌아간다

![image](https://assets.youngsu5582.today/obsidian/2026/11/27/154bdfcced09d64f9b7ac311fbc504ae.png)

```text
PooledByteBufAllocator
 └─ Arena        (구역, 여러 개)
     └─ Chunk    (allocateDirect 로 한 번에 받은 덩어리, 기본 4 MiB)
         └─ ByteBuf 하나가 쓰는 구간
```

그 대신 한 번 받은 청크를 쉽게 돌려주지 않는다. (Trade-Off)

`ByteBuf` 는 참조 카운트(`refCnt`)로 수명을 관리한다.
풀에서 받은 버퍼는 `release()` 로 카운트가 0 이 되면 풀로 반환되고, 빼먹으면 돌아오지 않는다. (누수 가능)

- 청크보다 큰 요청은 풀을 거치지 않고 요청 크기만큼 따로 잡고, `release()` 때 바로 해제한다.
- Netty 스레드에서 해제된 작은 버퍼는 청크로 바로 가지 않고 스레드 캐시에 먼저 보관된다.

## 돌아오지 않는 청크

`release()` 를 빠짐없이 불러도, JDK 가 세는 Direct memory 는 줄지 않을 수 있다!

=> 모니터링으로 보면 누수 같지만 누수가 아니다. 버퍼는 풀로 돌아갔고, 청크가 해제되지 않았을 뿐이다.

그래서 반환은 두 단계로 나눠 봐야 한다.

![image](https://assets.youngsu5582.today/obsidian/2026/11/26/d23f540b3ec38b6f651ff2d97d95eff5.png)

- 1단계 (버퍼 → 풀): `release()` 로 카운트가 0 이 되는 즉시 일어난다. 앱 코드가 책임지는 부분이고, 빼먹으면 진짜 누수다.
- 2단계 (청크 해제): Netty 가 정한 조건이 맞을 때만 일어난다. 앱 코드로 제어할 수 없다. 조건이 맞으면 Netty 가 청크를 버리면서 바로 메모리를 해제하고, JDK 한도에서도 뺀다.

> 해제된 청크가 OS 까지 돌아가는지는 C 메모리 할당기에 달렸다.
> musl(Alpine) 은 약 128 KiB 이상을 따로 mmap 해 주고 해제할 때 바로 OS 에 돌려주지만, glibc 는 다시 쓰려고 쥐고 있을 수 있다.

### 청크가 돌아가는 조건

청크는 "한 번 충분히 쓰였다가, 완전히 비었을 때" 만 해제된다.

- 충분히 쓰였다 = 사용률이 25% 에 닿은 적이 있다.
	- Netty 는 청크를 사용률별 목록으로 나눠 관리한다.
	- 새 청크는 시작 목록(`qInit`)에 들어가고, 사용률이 25% 에 닿아야 그 목록을 떠난다.
	- 시작 목록에 머문 청크는 비어도 돌아가지 않는다.
- 완전히 비었다 = 버퍼가 하나도 남지 않았다.

![image](https://assets.youngsu5582.today/obsidian/2026/11/27/71aa0ac4f4df7cdee09a38c52ec790e2.png)

코드로 보면 다음과 같다.

```java
// PoolArena 생성자 — 목록마다 (다음 목록, 최소 사용률, 최대 사용률)
q000 = new PoolChunkList<T>(this, q025, 1, 50, sizeClass.chunkSize);
qInit = new PoolChunkList<T>(this, q000, Integer.MIN_VALUE, 25, sizeClass.chunkSize);
…
q000.prevList(null);
qInit.prevList(qInit);

// PoolArena.allocateNormal — 새 청크는 시작 목록으로
qInit.add(c);

// PoolChunkList.move0 — 아래 목록으로 내려가다 더 내려갈 곳이 없으면
if (prevList == null) {
    // There is no previous PoolChunkList so return false which result in having the PoolChunk destroyed and
    // all memory associated with the PoolChunk will be released.
    assert chunk.usage() == 0;
    return false;
}

```

> Netty 4.1.135.Final
> 목록 만들기 · 연결 [PoolArena.java#L87-L99](https://github.com/netty/netty/blob/netty-4.1.135.Final/buffer/src/main/java/io/netty/buffer/PoolArena.java#L87-L99) · 새 청크 [PoolArena.java#L212-L216](https://github.com/netty/netty/blob/netty-4.1.135.Final/buffer/src/main/java/io/netty/buffer/PoolArena.java#L212-L216) · 청크 해제 [PoolChunkList.java#L146-L154](https://github.com/netty/netty/blob/netty-4.1.135.Final/buffer/src/main/java/io/netty/buffer/PoolChunkList.java#L146-L154)

> 새로 받은 청크를 조금 쓰고 바로 돌려주면, 다음 읽기에 다시 무거운 할당을 해야 한다.
> 그래서 새 청크를 시작 목록에 붙잡아 두는 것으로 보인다.

=> 청크는 잘 돌아가지 않는데, 한도에는 청크 단위로 올라간다.
그래서 남은 한도가 청크 하나보다 작아지면, 아주 작은 버퍼라도 새 청크가 필요한 순간 얻지 못한다.

## 직접 확인

위 내용에 대해 확인하기 위해, 실제 코드로 확인해보자.

실험은 JDK 21.0.6, Direct 한도 64 MiB 로 돌렸다.
관찰하기 쉽게 청크를 512 KiB(`maxOrder=6`)로 줄이고, 구역(arena)은 1개, 스레드 캐시는 껐다.

> 실험 코드와 출력 원본은 [netty-core-playground](https://github.com/youngsu5582/playground/tree/ad54a706aa11ac9851520c7d2f7ed5d855947cd9/netty-core-playground) 에 있다.
> 출력의 "상자" 는 청크, "칸" 은 버퍼, "계상된다" 는 한도에 더해진다는 뜻이다. 읽기 쉽게 빈 줄을 넣었고, 줄인 곳은 `…` 로 표시했다.

### 파트 1 — JDK 의 계산

```bash
JAVA_OPTS="-XX:MaxDirectMemorySize=64m" ./run.sh Lesson02DirectMemory 1
```

```text

=== 파트 1: JDK 의 계산 — 직접 버퍼 하나마다 한도에 계상된다 ===
시작   | JDK 예약량 = 0.00 MiB
8 MiB 버퍼 1개 할당 | JDK 예약량 = 8.00 MiB
8 MiB 버퍼 2개 할당 | JDK 예약량 = 16.00 MiB
8 MiB 버퍼 3개 할당 | JDK 예약량 = 24.00 MiB

-- 한도를 넘을 때까지 8 MiB 씩 계속 할당 (참조를 쥐고 있다)
할당 성공 개수 = 8  (64.00 MiB)
OOM 메시지     = Cannot reserve 8388608 bytes of direct buffer memory (allocated: 67108864, limit: 67108864)
실패한 할당 1회에 걸린 시간 = 539 ms  (JDK 가 GC 를 한 번 돌리고 잠깐씩 기다린 뒤 포기한다)

-- 참조를 모두 놓고 GC 를 돌리면?
참조 해제 + GC 후 | JDK 예약량 = 0.00 MiB  (JDK 직접 버퍼는 GC 가 회수한다)
```

버퍼 하나하나가 한도에 잡히고, 한도에 닿은 할당은 539 ms 걸렸다.
참조를 전부 해제하고 GC 를 돌리면 예약량이 0 으로 돌아온다.

### 파트 2 — 청크 단위로 잡히는 한도와 반납 조건

```bash
JAVA_OPTS="-XX:MaxDirectMemorySize=64m" ./run.sh Lesson02DirectMemory 2
```

```text
…
=== 파트 2: Netty 풀 — 한도에는 '상자(청크)' 단위로 계상된다 ===
청크(상자) 크기 = 0.50 MiB , 직접 구역(arena) 수 = 1
시작   | JDK 예약량 = 0.00 MiB | Netty 가 가진 상자 총량 = 0.00 MiB

-- 시나리오 2-A: 상자의 25% 도 안 쓴 채 모두 반납하면?
1 KiB 버퍼 1개 할당 | JDK 예약량 = 0.50 MiB | 상자 총량 = 0.50 MiB  <- 1 KiB 가 아니라 상자 한 개(0.50 MiB)가 예약됐다
1 KiB 버퍼 3개째    | JDK 예약량 = 0.50 MiB | 상자 총량 = 0.50 MiB  <- 같은 상자의 다른 칸을 썼으므로 늘지 않는다
3개 모두 release    | JDK 예약량 = 0.50 MiB | 상자 총량 = 0.50 MiB  <- 상자가 완전히 비었는데도 반납되지 않았다 (!)
…

-- 시나리오 2-D: 큰 버퍼 1개(64 KiB = 상자의 12.5%)만 쓰고 반납하면? (소스의 qInit 규칙 확인)
64 KiB 버퍼 1개 할당 | 이 풀이 예약한 양 = 0.50 MiB
release              | 이 풀이 예약한 양 = 0.50 MiB  <- 상자를 25% 도 쓴 적 없으면 비어도 남는다 (새 상자가 놓이는 qInit 은 비워도 반납하지 않는다)
…
```

- 1 KiB 를 요청해도 청크 하나(0.50 MiB)가 예약되고, 3개를 모두 `release()` 해도 그대로 남는다.
- 25% 에 닿은 적 없는 청크는 비어도 남는다 (충분히 쓰이지 않았다).

```text
-- 시나리오 2-C: 큰 버퍼(64 KiB)로 상자를 쓰고 모두 반납하면?
64 KiB 버퍼 4개 할당(상자의 50%) | 이 풀이 예약한 양 = 0.50 MiB | 상자 총량 = 0.50 MiB
3개 release (1개는 쥐고 있음)     | 이 풀이 예약한 양 = 0.50 MiB | 상자 총량 = 0.50 MiB  <- 칸 하나가 상자를 묶고 있다
마지막 1개도 release              | 이 풀이 예약한 양 = 0.00 MiB | 상자 총량 = 0.00 MiB  <- 큰 버퍼만 쓴 상자는 비면 반납된다
```

- 버퍼 하나가 남으면 청크 전체가 묶이고, 마지막 하나가 풀리면 반납된다.

### 파트 3 — 풀이 한도에 닿으면

```bash
JAVA_OPTS="-XX:MaxDirectMemorySize=64m" ./run.sh Lesson02DirectMemory 3
```


```text
…
=== 파트 3: … 풀을 한도까지 채우면 ===
16 KiB 버퍼 4096개를 쥔 상태에서 실패
Netty 상자 총량 = 64.00 MiB , JDK 예약량 = 64.00 MiB

OOM 메시지 = Cannot reserve 524288 bytes of direct buffer memory (allocated: 67108865, limit: 67108864)
-> 새 상자(0.50 MiB)를 예약하려는데 '한도 - 이미 예약량' 이 그보다 작아서 실패한다.
…
```

16 KiB 버퍼를 `OutOfMemoryError` 가 날 때까지 쥐고 늘린 실험이다.
실패한 요청은 16 KiB 가 아니라 청크 하나(524288 바이트 = 512 KiB)다.

=> 남은 여유가 청크 하나보다 작아지는 순간부터, 새 청크가 필요한 모든 할당이 실패한다.

## 흔한 오해

| 오해                            | 실제                                                                                   |
| ----------------------------- | ------------------------------------------------------------------------------------ |
| Direct 메모리는 GC 와 무관           | JDK Direct 버퍼는 GC 가 돌아야 해제된다(Cleaner). Netty 풀의 버퍼는 참조 카운트로 반납되지만 청크는 조건이 맞을 때만 해제된다 |
| Direct 가 힙보다 항상 빠르다           | 복사는 줄지만 할당 · 해제는 더 무겁다. 그래서 풀이 필요하다                                                  |
| `release()` 하면 메모리가 OS 로 돌아간다 | 버퍼가 풀로 돌아갈 뿐이다. 한도 계산(JDK 예약량)은 줄지 않을 수 있다                                           |
| 한도에 닿으면 즉시 OOM 이다             | GC 한 번과 최대 9번의 대기(약 0.5초) 뒤에 던진다                                                     |

처음의 질문으로 돌아온다.

> “힙은 남아 있는데 왜 메모리가 부족하다고 할까?”

1. Direct 한도는 힙과 따로 센다.
2. Direct 버퍼를 만들고 버려도 힙에는 수십 바이트 객체뿐이라 GC 가 돌 이유가 잘 생기지 않고, 힙 밖 메모리는 그대로 남는다.
3. Netty 풀에서는 한도에 청크 단위로 올라가고, 청크는 조건이 맞을 때만 해제된다.

=> 힙이 남아 있어도 한도는 따로 찬다. 한도가 청크 단위로 차므로, 남은 여유가 청크 하나보다 작으면 새 청크를 얻지 못한다.

## 다음 편

실제 장애에서는 한도가 이렇게 찬 상태에서 재시도가 새 연결을 열었고, TLS 핸드셰이크가 복호화용 버퍼를 달라고 하는 순간 `Cannot reserve 524288 bytes` 가 났다.
그런데 요청은 실패로 끝나지 않고 멈춰 버렸다. 2편에서는 그 이유를 따라간다.
