### 3줄 요약

1. Claude Code Mod는 Claude에게 지침을 주는 기능이라기보다, Claude Code 엔진의 이벤트에 TypeScript 함수를 연결하는 플러그인에 가깝다.
2. `tool.call`, `tool.check`, `ui.render`를 조합하면 도구 실행 기록·권한 확인·세션 패널을 한 기능으로 묶을 수 있다.
3. 직접 `command-log`를 만들어 보면서, Mod의 강력함보다 `next(e)`를 언제 호출하고 실패를 어떻게 처리할지가 더 중요하다는 것을 확인했다.

# Claude Code Mod로 도구 실행을 관찰하고 제어해보기

최근 Claude Code를 살펴보다가 `Mod`라는 기능을 알게 됐다. 이름만 보면 테마나 화면을 바꾸는 확장 기능처럼 느껴지지만, 실제로는 Claude Code 내부의 이벤트에 TypeScript 함수를 연결하는 **함수 훅 기반 플러그인**에 더 가깝다.

처음에는 “Hooks와 무엇이 다르지?”라는 생각이 들었다. 둘 다 특정 시점에 코드를 실행하고, 명령이나 권한을 제어할 수 있기 때문이다. 그래서 이번 글에서는 Mod를 단순히 소개하는 대신 다음 순서로 직접 확인해 봤다.

- Claude와 Claude Code의 역할을 나눠 보기
- Skills·`CLAUDE.md`·Hooks·Mod의 제어 지점 비교하기
- 이벤트와 `next(e)`의 흐름 이해하기
- Bash 실행 기록과 GitHub 쓰기 확인을 붙인 `command-log` 작성하기
- 실제로 써 보면서 확인한 한계와 운영상의 주의점 정리하기

이 글에서 다루는 Mod API는 Early Access 성격이 있다. 현재 공식 문서는 터미널에서 Mod를 사용하려면 Claude Code `2.1.287` 이상을 사용하라고 안내하고, 예제 저장소는 `2.1.294` 이상을 전제로 한다. Claude Code 릴리스에 따라 API가 바뀔 수 있으므로, 코드를 그대로 복사하기보다 현재 설치한 버전의 타입과 공식 예제를 함께 확인하는 편이 안전하다.

또 하나 중요한 점은 Mod가 현재 사용자의 권한으로 실행된다는 것이다. 공식 문서가 설명하듯 Mod는 파일을 읽고 쓰거나 프로세스를 시작하고 네트워크 요청을 보낼 수 있다. 따라서 marketplace나 저장소의 출처를 확인하지 않은 Mod는 설치하지 않는 편이 좋다. 예제도 로컬에서 동작을 확인한 뒤, 실제 계정과 저장소에 적용할 범위를 따로 검토해야 한다.

## 먼저 나눠 보기: Claude와 Claude Code

Claude는 모델이다. 사용자가 보낸 프롬프트를 읽고 다음에 할 일을 텍스트나 도구 호출 형태로 반환한다. 모델 자체가 내 컴퓨터의 파일을 읽거나 `git` 명령을 실행하는 것은 아니다.

Claude Code는 모델과 내 컴퓨터 사이에서 동작하는 프로그램이다.

```text
사용자
  ↓ 프롬프트
Claude Code
  ├─ 프롬프트 조립
  ├─ Claude API 호출
  ├─ 모델이 반환한 도구 호출 검사
  ├─ 로컬에서 실제 도구 실행
  └─ 실행 결과를 다시 Claude에 전달
        ↓
      Claude의 다음 판단
```

![Claude와 Claude Code 사이에서 도구 호출이 오가는 흐름](https://assets.youngsu5582.today/obsidian/2026/10/09/1d7babb4c4f74b71d20ba350c4e5d28e.png)

예를 들어 Claude가 `gh pr list`를 실행하자고 하면, Claude는 도구 호출을 반환하고 Claude Code가 실제 실행을 담당한다. 이 사이에 권한 검사나 기록을 넣을 수 있다는 점이 Mod를 이해하는 출발점이다.

## 사용자의 제어 지점

Claude Code를 사용자가 제어하는 방법은 한 가지가 아니다. 각각 영향을 미치는 위치가 다르다.

| 기능        | 주로 영향을 미치는 곳                     | 성격                                |
| ----------- | ----------------------------------------- | ----------------------------------- |
| Skills      | 모델에 제공하는 지침과 작업 방식          | Claude가 읽고 따르는 컨텍스트       |
| `CLAUDE.md` | 프로젝트·사용자 규칙                      | 모델이 참고하는 지속적인 규칙       |
| 기존 Hooks  | 특정 도구 실행 전후의 외부 스크립트       | 셸 명령으로 연결하는 절차           |
| Mod         | Claude Code 엔진 이벤트와 플러그인 런타임 | 이벤트 체인·권한·UI에 연결하는 코드 |

예를 들어 “GitHub에 쓰는 명령은 실행 전에 물어봐”라는 요구가 있다고 하자.

- Skill이나 `CLAUDE.md`는 Claude에게 그렇게 하라고 설명한다.
- Hook이나 Mod는 Claude Code의 실행 흐름에 검사 코드를 붙인다.

따라서 후자는 모델이 해당 지침을 잊었는지와 별개로 실행 경로를 검사할 수 있다. 다만 Mod가 모든 보안 경계를 자동으로 해결해 주는 것은 아니다. 어떤 이벤트를 가로채는지, `next`를 호출하는지, 오류가 났을 때 어떻게 답하는지를 직접 설계해야 한다.

## Mod는 무엇인가

현재 [Claude Code 공식 Mods 문서](https://code.claude.com/docs/en/plugins/mods/overview)와 공식 저장소의 `mods` 예제를 기준으로 보면, Mod는 다음과 같은 구조를 가진다.

- `.claude-plugin/plugin.json`으로 플러그인 메타데이터를 정의한다.
- `hooks/hooks.json`에서 로드할 모듈을 지정한다.
- TypeScript 모듈에서 `register(on, options)`를 내보낸다.
- `on(event, handler)` 형태로 이벤트에 함수를 등록한다.
- 핸들러는 보통 `($, e, next)`를 받고, `$`를 통해 Claude Code 런타임 기능을 요청한다.

공식 저장소에도 `/diff` 패널을 제공하는 내장 Mod와 보안 정책을 적용하는 Mod가 같은 구조로 들어 있다. 다만 Mod는 플러그인 안에 Skills·Agents·MCP 서버와 함께 묶일 수 있고, 기존 설정 Hook과는 실행 위치가 다르다. 즉, Mod는 “프롬프트를 잘 쓰기 위한 문서”라기보다 Claude Code 런타임에 붙는 작은 프로그램으로 보는 편이 이해하기 쉽다.

## 이벤트와 `next(e)`

Mod를 이해할 때 가장 중요한 것은 이벤트 이름보다 `next(e)`다. 여러 핸들러가 연결된 체인 안에서 다음 단계로 이벤트를 넘기는 함수다.

```text
이벤트 발생
  ↓
Mod A handler
  ├─ 바로 결과 반환 → 여기서 흐름 종료
  └─ await next(e)
       ↓
     Mod B handler
       ├─ 결과 반환
       └─ await next(e)
            ↓
          Claude Code의 원래 동작
```

`tool.call`을 예로 들면 다음과 같이 실행 전후에 코드를 넣을 수 있다.

```typescript
on("tool.call", { tool: "Bash" }, async ($, e, next) => {
  // 실행 전
  const startedAt = await $.clock.now();

  // 다음 훅과 Claude Code의 원래 실행으로 넘긴다
  const result = await next(e);

  // 실행 후
  const elapsed = (await $.clock.now()) - startedAt;
  console.log(e.command, elapsed, result);

  // 결과를 돌려줘야 원래 흐름이 유지된다
  return result;
});
```

반대로 `next(e)`를 호출하지 않고 `{ deny: '위험한 명령' }`을 반환하면 뒤의 실행으로 넘어가지 않도록 만들 수 있다. 그렇다고 모든 이벤트에서 같은 반환값을 사용하면 되는 것은 아니다. 이벤트별 입력과 반환 타입은 현재 Claude Code가 제공하는 타입 정의를 기준으로 확인해야 한다.

![Claude Code 이벤트 흐름을 정리한 그림](https://assets.youngsu5582.today/obsidian/2026/10/07/968bf86e2efc1bf51c211795b6a8f334.png)

## 어떤 이벤트를 사용할까

이번 예제에서 사용한 이벤트는 다섯 가지다.

| 이벤트          | 예제에서 한 일                             |
| --------------- | ------------------------------------------ |
| `session.start` | `/command-log` 슬래시 커맨드 등록          |
| `command.run`   | 패널 열기·닫기                             |
| `tool.call`     | Bash 명령의 성공 여부와 실행 시간 기록     |
| `tool.check`    | GitHub에 쓰는 Bash 명령 실행 전 `ask` 반환 |
| `ui.render`     | 기록된 명령 목록을 패널에 렌더링           |

이 정도만 조합해도 “실행을 기록하고, 위험한 범주는 확인하고, 화면으로 보여 주는” 작은 도구가 된다.

## 예제: `command-log` 만들기

이번에 만든 예제의 전체 코드는 [youngsu5582/playground의 `claude-mod-playground`](https://github.com/youngsu5582/playground/tree/main/claude-mod-playground)에서 볼 수 있다.

목표는 단순하게 잡았다.

- `/command-log`로 패널을 연다.
- Claude가 실행한 Bash 명령과 성공 여부·소요 시간을 기록한다.
- 상태줄에는 전체 명령 수와 실패 수를 보여 준다.
- `gh pr comment`, `gh issue create`처럼 GitHub에 쓰는 명령은 실행 전에 권한을 묻는다.

### 실행 환경

예제 저장소의 README에서는 Claude Code `2.1.294` 이상을 전제로 한다. 이 기능은 Early Access이므로 실제로는 현재 설치한 버전에서 다시 확인해야 한다.

```bash
claude --plugin-dir ./command-log
```

세션이 열린 뒤 다음 커맨드를 입력한다.

```text
/command-log
```

파일을 수정하면 `--plugin-dir`로 실행한 세션에서 Mod가 다시 로드된다. 공식 문서의 현재 설치 형식으로 설치하려면, 저장소 루트의 `marketplace.json`에 선언한 marketplace 이름을 사용한다.

```text
/plugin install command-log@youngsu5582-playground
```

예제 저장소의 README에는 이전 CLI 문법인 `--marketplace youngsu5582/playground`도 기록되어 있다. Claude Code 버전에 따라 설치 문법이 달라질 수 있으므로, 설치 전 `/plugin`의 Discover 화면과 [공식 설치 문서](https://code.claude.com/docs/en/plugins)를 함께 확인하자.

### `plugin.json`

먼저 플러그인이라는 사실과 사용자 설정을 선언한다.

```json
{
  "name": "command-log",
  "version": "0.1.0",
  "description": "Bash 명령을 패널과 상태줄에 보여 주고 GitHub 쓰기 전에 묻는다",
  "author": {
    "name": "youngsu5582"
  },
  "types": "./types/index.d.ts",
  "userConfig": {
    "askGhWrite": {
      "type": "boolean",
      "title": "gh 쓰기 전에 묻기",
      "description": "GitHub에 쓰는 gh 명령 전에 권한 프롬프트를 띄운다",
      "default": true
    }
  }
}
```

`userConfig.askGhWrite`는 사용자가 기능을 켜고 끌 수 있게 하는 값이다. 코드에서 `options.askGhWrite !== false`로 읽기 때문에 설정을 생략하면 기본적으로 확인한다.

### `hooks.json`

어떤 TypeScript 모듈을 읽을지 지정한다.

```json
{
  "modules": ["./register.tsx"]
}
```

### 상태 타입과 저장소

실행 기록은 Mod가 제공하는 상태 API에 저장한다. 최대 20개만 유지해 패널이 지나치게 커지지 않도록 했다.

```typescript
import { atom, read, update } from "claude-code";
import type { Register } from "claude-code";

export type CommandRecord = {
  command: string;
  isOk: boolean;
  ms: number;
};

const records = atom({ plugin: "command-log", key: "records" } as const, []);

const MAX_RECORDS = 20;
```

별도의 `types/index.d.ts`에서는 플러그인 상태에 `command-log`의 기록 타입을 추가한다.

```typescript
declare module "claude-code" {
  interface PluginState {
    "command-log": { records: CommandRecord[] };
  }
}
```

여기서 `atom`은 단순한 전역 변수와 다르다. 세션에서 Mod를 다시 읽더라도 엔진이 제공하는 상태 저장소를 통해 기록을 유지할 수 있다. 실제 상태 수명과 초기화 시점은 설치한 Claude Code 버전에서 확인하는 것이 좋다.

### `/command-log` 등록과 패널 열기

세션이 시작되면 슬래시 커맨드를 등록한다.

```typescript
const PANE = "command-log";

export const register: Register = (on, options) => {
  const isAskGhWrite = options.askGhWrite !== false;

  on("session.start", async ($, e, next) => {
    await $.command.register({
      name: "command-log",
      description: "실행한 Bash 명령을 패널로 본다. off를 붙이면 닫는다",
      argumentHint: "[off]",
    });
    return next(e);
  });

  on("command.run", { command: "command-log" }, async ($, e) => {
    if (e.args.trim() === "off") {
      await $.ui.close({ id: PANE });
      return { text: "명령 기록 패널을 닫았다." };
    }

    await $.ui.open({ id: PANE, title: "명령 기록", focus: true });
    return { text: "명령 기록 패널을 열었다. 닫으려면 /command-log off" };
  });
};
```

여기서 `command.run`은 우리가 등록한 커맨드의 실행을 직접 처리한다. 이 이벤트에서는 패널을 열고 닫는 것이 목적이므로 `next`를 호출하지 않고 결과를 반환한다.

### `tool.call`로 실행 기록 남기기

이제 Bash 실행 앞뒤에 기록 로직을 붙인다.

```typescript
on("tool.call", { tool: "Bash" }, async ($, e, next) => {
  const startedAt = await $.clock.now();
  const result = await next(e);
  const ms = (await $.clock.now()) - startedAt;

  const isOk = result.deny === undefined && result.isError !== true;

  await update($, records, (list) =>
    [...list, { command: e.command, isOk, ms }].slice(-MAX_RECORDS),
  );

  $.ui.status(statusOf(await read($, records)));
  return result;
}).catch(($, e, next) => next(e));
```

핵심은 세 가지다.

1. `await next(e)` 앞에서 시작 시간을 기록한다.
2. `next(e)`가 반환한 결과로 성공 여부를 판단한다.
3. 기록 자체가 실패해도 마지막 `catch`에서 `next(e)`를 호출해 원래 Bash 실행을 방해하지 않는다.

이 코드에서 측정되는 시간은 단순히 실제 프로세스가 실행된 시간만은 아닐 수 있다. `next(e)` 안에 다른 훅이나 권한 판정 과정이 포함될 수 있기 때문이다. 예제 저장소의 테스트에서도 PreToolUse 셸 Hook 유무에 따라 `ls` 측정값이 달라지는지 관찰하도록 했다.

![Mod의 파일 구성과 코드 흐름](https://assets.youngsu5582.today/obsidian/2026/10/09/75434d8369f2db91b1edac87d0ce41ef.png)

상태줄 문자열은 별도 함수로 분리했다.

```typescript
const statusOf = (list: CommandRecord[]): string => {
  const failed = list.filter((one) => !one.isOk).length;
  return failed > 0 ? `명령 ${list.length} · 실패 ${failed}` : `명령 ${list.length}`;
};
```

### `tool.check`로 GitHub 쓰기 전에 묻기

실행 기록과 별개로, GitHub에 쓰는 명령은 실행 전에 확인하고 싶었다.

```typescript
on("tool.check", { tool: "Bash" }, async ($, e, next) => {
  const command = (e.input as { command?: string }).command ?? "";

  if (isAskGhWrite && isGhWrite(command)) {
    return {
      decision: "ask",
      reason: "gh로 GitHub에 쓰는 명령이다",
    };
  }

  return next(e);
}).catch(() => ({ decision: "ask" }));
```

`gh` 명령을 판별하는 함수는 너무 넓게 잡지 않았다.

```typescript
export const isGhWrite = (command: string): boolean => {
  if (/\bgh\s+api\b/.test(command)) {
    return (
      /(-X|--method)[\s=]*(POST|PUT|PATCH|DELETE)\b/i.test(command) ||
      /\s(-f|-F|--field|--raw-field|--input)\s/.test(command)
    );
  }

  return /\bgh\s+(pr|issue)\s+(create|comment|edit|close|merge|review)\b/.test(command);
};
```

읽기 명령인 `gh pr list`는 그대로 통과시키고, PR·Issue를 만들거나 수정하는 명령과 `gh api`의 쓰기 요청만 확인 대상으로 삼는다.

여기서 `catch`는 기록용 `tool.call`과 반대로 **확인하는 쪽으로 닫혀 있다**. 권한 판정 코드가 실패했는데 명령을 그대로 통과시키면 안전한 기본값이 아니기 때문이다.

![GitHub 쓰기 명령에 권한을 묻는 화면](https://assets.youngsu5582.today/obsidian/2026/10/09/6314b4fee685485c06a249bfd391acb4.png)

### `ui.render`로 패널 그리기

마지막으로 상태를 패널에 그린다.

```tsx
on("ui.render", { component: "Pane", requestId: PANE }, async ($, e) => {
  const { Box, Text } = $.ui.resolve(e);
  const list = await read($, records);

  return (
    <Box flexDirection="column">
      {list.length === 0 && <Text dimColor>아직 실행한 명령이 없다.</Text>}
      {list.map((one, index) => (
        <Text key={`record-${index}`} color={one.isOk ? undefined : "error"} wrap="truncate-end">
          {one.isOk ? "✓" : "✕"} {one.command} · {one.ms}ms
        </Text>
      ))}
    </Box>
  );
});
```

`records`가 바뀌면 패널이 다시 렌더링된다. UI를 직접 그리는 코드처럼 보이지만, 터미널과 Claude Desktop에서의 화면별 렌더링 차이는 `$.ui.resolve(e)`가 제공하는 컴포넌트가 담당한다. VS Code 확장이나 `claude -p`처럼 Hook은 실행되지만 UI를 그리지 않는 환경도 있으므로, 패널이 모든 실행 환경에 나타난다고 가정하면 안 된다.

## 직접 실행해 본 결과

예제 저장소에는 자동 테스트와 세션에서 직접 확인하는 테스트 목록을 함께 적어 두었다.

| 확인 항목        | 관찰한 내용                                                                   |
| ---------------- | ----------------------------------------------------------------------------- |
| 커맨드 등록      | 세션을 열면 `/command-log`가 목록에 나타난다.                                 |
| 패널 열기·닫기   | `/command-log`와 `/command-log off`가 각각 동작한다.                          |
| 실행 기록        | `ls`, `git status`, `false` 같은 Bash 실행이 성공·실패 아이콘과 함께 쌓인다.  |
| 실행 시간        | `next(e)` 안에서 실행되는 다른 Hook·권한 처리 시간까지 포함될 수 있다.        |
| GitHub 쓰기 확인 | `gh pr comment`, `gh issue create`를 실행하기 전에 확인 프롬프트가 나타난다.  |
| 핫 리로드        | `--plugin-dir` 세션에서 코드를 수정하면 다음 턴에 변경된 UI를 확인할 수 있다. |

실행 기록을 남기는 기능 자체는 작지만, Mod의 위치를 확인하기에는 좋은 예제였다. Claude가 “이 명령을 실행해도 될까?”라고 판단하는 프롬프트 영역이 아니라, Claude Code가 도구를 실행하기 직전과 직후에 위치하기 때문이다.

## Hooks와 Mod를 나란히 놓고 보기

둘을 완전히 대체 관계로 볼 필요는 없다.

```text
CLAUDE.md / Skill
  → 모델에게 규칙과 배경을 제공

기존 Hook
  → 특정 도구 생명주기에 셸 스크립트 연결

Mod
  → Claude Code 이벤트 체인에 TypeScript 로직 연결
  → 권한·상태·패널·커맨드까지 하나의 플러그인으로 묶음
```

모델이 알아야 하는 설명은 Skill이나 `CLAUDE.md`에 두는 편이 자연스럽다. 운영 정책을 도구 실행 경로에서 검사해야 한다면 Hook 또는 Mod를 검토한다. 화면에 현재 상태를 보여 주거나 세션 명령과 상태를 함께 묶고 싶다면 Mod가 더 적합할 수 있다.

다만 Mod 하나에 모든 규칙을 넣으면 또 다른 복잡한 애플리케이션이 된다. 작은 이벤트 하나를 붙일 때도 다음을 먼저 정하는 편이 좋다.

- 어떤 이벤트를 관찰할 것인가
- `next(e)` 전후 중 어디에 로직을 둘 것인가
- 결과를 바꿀 것인가, 기록만 할 것인가
- 오류가 나면 계속 진행할 것인가, 확인을 요구할 것인가
- 상태가 세션을 넘어가도 되는가
- 사용자가 끌 수 있어야 하는가

## 만들면서 알게 된 것

### 1. `next(e)`는 단순한 다음 함수 호출이 아니다

`next(e)`를 호출하느냐 마느냐에 따라 원래 Claude Code 동작까지 이어질 수도 있고, 현재 Mod에서 흐름이 끝날 수도 있다. 따라서 로깅 Mod라도 실수로 `return next(e)`를 빼먹으면 명령이 실행되지 않는다.

### 2. 관찰과 차단의 오류 정책은 다르게 잡을 수 있다

이번 예제에서는 다음처럼 분리했다.

- 실행 기록 실패: 기록만 포기하고 Bash는 계속 실행한다.
- 권한 판정 실패: 안전하게 `ask`로 처리한다.

모든 오류를 같은 방식으로 처리하지 않고, 기능의 목적에 따라 fail-open과 fail-closed를 선택해야 한다.

### 3. 실행 시간에는 주변 단계가 포함될 수 있다

`tool.call`의 `next(e)` 주변에서 시간을 재면 실제 Bash 프로세스 시간만 측정한다고 단정할 수 없다. 다른 Hook, 권한 판정, 엔진 내부 처리까지 포함될 수 있다. 측정값을 운영 지표로 사용할 때는 무엇을 포함하는지 먼저 정의해야 한다.

### 4. Early Access 기능은 버전 고정과 테스트가 중요하다

Mod는 일반적인 TypeScript 라이브러리처럼 API가 오래 고정됐다고 가정하기 어렵다. 이벤트 이름, `$`의 기능, 타입 선언, 테스트 명령이 릴리스에 따라 달라질 수 있다.

그래서 예제 저장소에는 다음을 함께 남겼다.

- 동작을 확인한 Claude Code 버전
- `claude plugin test`로 실행하는 자동 테스트
- 실제 세션에서 확인하는 T1~T7 시나리오
- API가 바뀌었을 때 다시 확인할 README

## 마무리

Claude Code Mod는 Claude에게 새로운 지식을 넣는 기능이라기보다, Claude Code가 모델과 도구 사이에서 동작하는 지점을 사용자가 확장할 수 있게 해 주는 인터페이스에 가깝다.

이번에는 Bash 실행 기록, 상태줄, 패널, GitHub 쓰기 전 확인만 붙여 봤다. 이 정도만으로도 다음과 같은 방향을 생각해 볼 수 있다.

- `git push --force`를 감지해 `--force-with-lease`를 먼저 제안하는 안전장치
- 작업 중인 PR의 리뷰 상태와 미답변 코멘트를 보여 주는 패널
- 토큰 사용량·컨텍스트 공간·최근 명령을 보여 주는 상태줄
- 도구 결과에 포함된 API 키나 비밀번호를 Claude에게 전달하기 전에 마스킹하는 처리
- 홈서버 배포 전 변경 범위와 헬스체크 결과를 확인하는 패널

중요한 점은 Mod를 많이 붙이는 것이 아니다. Claude Code의 어떤 경계를 사용자가 실제로 관찰하거나 통제하고 싶은지 먼저 정하고, 그 경계에 가장 작은 이벤트 체인을 붙이는 것이다.
