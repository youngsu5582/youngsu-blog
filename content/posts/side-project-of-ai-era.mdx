22년 11월 즈음 ChatGPT 가 출시하며, 대 AI 시대가 찾아온지도 어언 4년이 지나버렸다.
내가 인지하는 LLM 이 코딩으로 나를 이기기 시작했다고 생각한건 Opus 4.6 정도부터 였던거 같다.

그전의 LLM 들은 단건 물어보는 요청은 잘 해줬지만,
코드 전부를 관리하거나 제어하는 것에 어려움이 있었다.

- interface 를 구현한 클래스들에 새롭게 메서드 추가해달라고 하면, 누락
- 죽어도, 공백을 넣거나 오타 생성
- 비동기나 이벤트로 인해 연결이 끊어져있으면 추적 X
- 코드를 다 이해하고 작업하기에는 부족한 컨텍스트

Opus 4.6 은 달랐다.

- 1M 토큰 컨텍스트 지원
- 에이전틱 코딩 능력 개선

그보다, 도구를 활용하며 진짜 코드를 짠다! 가 느껴졌던거 같다.
옛날처럼, 뚝뚝 끊기면서 채팅으로 이어붙인게 아니라 직접 수정하고 테스트하며 고쳐나갔다.

그 무렵 `Ralph loop` 라는 것도 유행했다. 명세만 잘하면 끝까지 개발을 완수하는 방식이다.

하지만, 그도 의미가 없어진게 Fable & Mythos 라는 플래그십 모델이 나타나며 잘 짜여질 필요도 없이
어느정도면 스스로 판단하고, 뚝딱 만들어내버렸다.

![image](https://assets.youngsu5582.today/obsidian/2026/11/13/fa4f9e236c669bf6fe2d9eed98631182.png)


Fable 은 5.2 까지 나오면서 계속 진행형이다.

## 왜 사이드 프로젝트를 하지 않는가

그러면, 도대체 왜 사이드 프로젝트를 하지 않는가?
코드의 비용이 이다지도 낮아지고, 완성 시간도 짧아지고, 심지어 병렬도 가능한데!!

[2025 회고 - 사이드 프로젝트 작게 작게 완성 시켜보기](https://www.youngsu5582.today/posts/2025-reflection#233-%EC%82%AC%EC%9D%B4%EB%93%9C-%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8-%EC%9E%91%EA%B2%8C-%EC%9E%91%EA%B2%8C-%EC%99%84%EC%84%B1-%EC%8B%9C%EC%BC%9C%EB%B3%B4%EA%B8%B0)

작년 회고에서 올해는 반드시 사이드 프로젝트를 완성시켜보겠다고 했다.

### 시도

사실, 올해 상반기에 다양한 사이드 프로젝트를 나름대로 해보려고 했다.

![image](https://assets.youngsu5582.today/obsidian/2026/11/13/7cdfaf56e095ba337d945d9ad89baeae.png)

3월에는 한창 책을 읽을 때, 맘에 드는 독서 기록 서비스를 못찾아서 만들려고 했었다.

![image](https://assets.youngsu5582.today/obsidian/2026/11/13/c1e789c26554c7000b2aeaf2dada8cee.png)

6월에는 내가 생성하는 다양한 데이터들

- AI 사용 기록
- 브라우저 탐구 기록
- 운동 데이터 (자전거, 수영)
- 사진 촬영 기록
- 옵시디언 기록

등을 내가 관리하려고 했었다.

### 결과

둘다 최종적으로는 실패였다.
실패한 이유를 하나씩 들어보겠다.

#### 독서 기록 서비스

이 프로젝트는 두가지 동기에 의해서 시작했다.

1. 사이드 프로젝트 해보고 싶다!
2. 요새, 책을 많이 읽으니까 & 책을 읽기 위해서 이를 돕는 서비스를 만들자!

처음에는 호기롭게 요구사항을 설계하고, 기능들을 개발해나갔다.

하지만... `독서 기록 저장` 관련 기능 개발을 하다보니, 그냥 CRUD 였다.
흥미가 떨어지지 않기 위해 욕심을 부렸다.

![image](https://assets.youngsu5582.today/obsidian/2026/11/13/5a00ada8bf601d91dccdc4875c4ce495.png)

현업에서 써보지 못한, Elasticsearch 나 Batch, K8s 를 써보려고 했다.

![image](https://assets.youngsu5582.today/obsidian/2026/11/13/9bcec128653f516f54970818cf4d63bb.png)

그러다보니, 오히려 배보다 배꼽이 더 커졌다.
사이드 프로젝트에서 써보기 위해서 "Elasticsearch 가 뭔지...", "명령어는 뭐가 있는지", "인덱스 적용"
와 함께 자연스레 흥미가 떨어지고 사라져갔다.

#### 일상 데이터 기록 서비스

3개월 정도가 지나고, 정말 다시 사이드 프로젝트를 해봐야겠다!
-> 정말 필요한 서비스를 만들면 흥미가 조금 떨어져도 계속 개발하지 않을까?

이때 당시, 미니 PC 를 구입하면서
나만의 self-hosted 서비스를 만들어 데이터를 관리하고 싶다는 의지도 충분했다.

실제로, 커밋을 168개나 하는등 나름대로 애정을 가지고 아직도 홈서버에 배포가 되어있고

![image](https://assets.youngsu5582.today/obsidian/2026/11/13/bceb517bafd21e2c18ad189ea52f3cc9.png)

![image](https://assets.youngsu5582.today/obsidian/2026/11/13/62ad2490f05e85ee24094472413476c3.png)

데이터를 계속 수집하고 있다.
하지만, 이 역시도 지금 개발을 멈췄고 두 가지 이유가 있다.

첫 번째 이유는 다소 들으면, 어이가 없을수 있지만? 
Strava 가 무료 API 제공을 중단했다. 😑

![image](https://assets.youngsu5582.today/obsidian/2026/11/13/5233bcbf3e88e5b62fc5824ac3b86cb8.png)

Provider 가 사라지면서, 새로운 Provider 를 찾아야 하고 고민하면서 의욕이 떨어져갔다..

그리고, 두 번째로는 구조가 나에게 너무 어려웠다.

![image](https://assets.youngsu5582.today/obsidian/2026/11/13/8b5c5c09a82b716d58a0bb4fbc4af0cd.png)

메달리온 아키텍처에 영감을 받아 도입했었다.

- 데이터를 바로 가공하지 않고, 단계별 가공해서 원하면 새롭게 구성할 수 있다는게 매력적이었다.
- 큰 데이터 처리 흐름을 경험해보고 싶었다.

하지만, 기능을 개발하는 시간보다 메달의 경계를 고민하거나,
경계 구분에서 나온 코드를 작성하는데 더 시간이 오래 걸리게 되었다.

#### 얻은 교훈

1. 진짜 하고싶은 사이드 프로젝트를 하자.

스펙을 위해, 사이드 프로젝트를 해야 한다는 부담감이 아닌 하고 싶은걸 하자.

2. 새로 배워야 하는 내용을 하지 말자.

사이드 프로젝트를 하는게 아니라, 학습이 주가 되어버렸다.
학습을 제 1목적으로 하는 프로젝트가 아니라면, 장기적인 사이드 프로젝트에 학습을 최대한 많이 넣지 말자.

3. 처음에는 쉽고, 나중에는 언제든 이어서 할 수 있는 주제를 하자.

`일상 데이터 기록 서비스`는 처음부터 메달리온 아키텍처를,
`독서 기록 서비스`는 한 페이즈를 넘길때마다 `Batch` -> `K8s` 를 바로 접근했다.

## 새로운 시작

9월달에 새로운 프로젝트를 시작했다.

서비스에 대해 간단한 소개를 해보자면,
`AI 요청 로직을 각 프로젝트에서 작성하지 않게 Gateway 처럼 모아놓은 서비스` 이다.

![image](https://assets.youngsu5582.today/obsidian/2026/11/14/422295214cba1d71c5b980e59fa81d3a.png)

> 자세한 내용은 [저장소](https://github.com/youngsu5582/personal-ai-workbench#%EC%99%9C-%EB%A7%8C%EB%93%A4%EA%B2%8C-%EB%90%98%EC%97%88%EB%82%98%EC%9A%94)를 참고하자.

### 이 주제를 선택한 이유

위 `얻은 교훈` 에서 생각한 내용들과 부합했다.

1. 진짜 하고싶은 사이드 프로젝트를 하자.

사이드 프로젝트나, 필요한 코드를 작성하면서
매번 직접 OpenAI 호출이나, Gemini 호출등의 코드를 작성해야했다.

- 코드보다는 매번 `API KEY`를 env 나 `application.yml` 등에 세팅하고 관리를 해야했다.
- 요청된 결과를 저장할 수 없거나, 비용을 정확히 추적하기 어려웠다.

=> 이런 점들을 통해 내가 사용하는 AI 로직을 모듈화 처럼 서비스를 만들고 싶었다.

2. 새로 배워야 하는 내용을 하지 말자.

현재, 회사에서 LLM 콘텐츠 생성 서비스 업무를 맡고 있다.
도메인 적으로도, 코드 적으로도 지식이 쌓여있고 백로그가 쌓여 있다.

이로 인해, 두가지를 얻을 수 있다.

- 기존 코드가 아닌, 처음부터 설계를 했다면 어떻게 설계 했을지
-> 이를 통해, 현재 회사의 코드를 어떻게 개선할 지 고민하게 된다.

- 현재 코드에서, 어떤 기능과 서비스를 확장 할 수 있을지
-> 회사 코드에 바로 도입하기 전 테스트 및 고려사항을 고민할 수 있다.

3. 처음에는 쉽고, 나중에는 언제든 이어서 할 수 있는 주제를 하자.

처음에는 이미 알고 있는 도메인 지식이기 때문에 어렵지 않게 코드를 빠르게 확장해나갈 수 있다.

그 후, 새로운 도전들을 해나갈 수 있다.

- OAuth 2.1 구축
- k3s, k8s 배포
- MCP, Agent Core
- 다른 언어에서 사용 가능하게 SDK 제공
- GPU Lambda 구축 + 오픈소스 처리

이미 많은 코드가 구축되어 있기 때문에, `빨리 만들어야 할 거 같은데..?` 같은 부담감을 느끼지 않는다.

## 마무리

처음의 질문으로 돌아가보면, 코드의 비용은 정말 낮아졌고, 더 낮아질 수도 있다고 생각한다.
사이드 프로젝트가 멈춘 곳은 코드가 아니었다.

- 독서 기록 서비스 : 흥미를 붙이려고 넣은 기술을 이해하는 데서 멈췄다.
- 일상 데이터 기록 서비스 : 메달의 경계를 어디에 둘지 고민하는 데서 멈췄다.

=> AI 가 낮춰준 건 코드를 쓰는 비용이지, 내가 이해하고 계속 하고 싶어하는 비용이 아니었다.

다른 사람들을 위해서나 같이 할 수 있는 사이드 프로젝트가 있다면 해도 되지만
그런게 없지만 사이드 프로젝트를 하고 싶다면 '자신만을 위한, 1명이라도 반드시 사용하는' 서비스를 만들어보자.
