## 10:50 — "AI야, 네 글 너무 밤티나"

> 한줄 평 : 글쓰기 같은 주관적 영역도, 정량적 평가를 추출해(정규식 검사) LLM 의 확률적이 아닌 명확한 결과를 이끌어 낼 수 있다.

- 발표자
	- 우아한형제들에서 테크니컬 라이팅을 검수하고 관리하는 DR(Developer Relations) 매니저
	- skills(AI 에게 줄 작업 지침을 파일로 묶어 둔 것)를 전사 차원에서 쓸 수 있게 설계하고 공유하는 개발자
	- 우아한테크코스에서 프론트엔드 개발자들을 가르치고, 그 과정을 책으로 집필중인 교육자

### DR 매니저 - 자주 남긴 검수 의견

테크니컬 라이팅을 하면 주로 남기는 피드백은 공통적이었다.

- 독자와 목적 : 도입부에 배경, 대상 독자, 읽고 얻을 것
- 근거 : 주장의 이유와 수치, 사례
- 제목과 본문 : 결론 먼저, 제목만 읽어도 주제를 알 수 있게

### 규칙만 적어 주면 AI 가 알아서 지킬까?

자주 남긴 검수 의견들을 스킬에 지침으로 옮겨 담았다.
-> 지침들이 하나씩 계속 늘어나게 되었다.
-> 지침들이 쌓여가니, 원래 지켜지던 것들도 자주 놓치게 되었다.

=> 그래서, 순서를 바꾸게 되었다.

1. 정규식 탐지기가 먼저 밑줄을 긋는다. (번역 투, 장문 등)
2. 보조 AI 둘이 "AI 티" 와 "문장 규칙" 을 나눠 지적과 수정안을 낸다.
3. 메인 AI 는 지적과 수정안 중 확인해야 하는 요소를 고르기만 한다.

> 후보는 탐지기가 모으고, AI 는 판단과 선택만 한다.

> skills 의 자세한 내용은 나중에 올라올 발표 영상을 참고하자.

### 왜 스킬이 필요한가?

위 내용을 기반으로 아래와 같은 흐름의 스킬을 만들었다.

> 아래 그림은, 찍은 발표 사진을 기반으로 LLM 에게 정리시킨 그림입니다.

![글쓰기 스킬의 흐름](https://assets.youngsu5582.today/obsidian/2026/11/08/7e3bd2ce879e2e16c0861b6e39c2b324.png)

만든 스킬로 블라인드 테스트를 했다. 사내 구성원들에게 아래 네 글 중 어떤 글이 제일 괜찮은지 블라인드로 투표를 받았다.

- LLM 도움 없이 직접 고친 글 / 스킬로 고친 글 / LLM 이 고친 글 / 원문

직접 고친 글과 스킬로 고친 글이 1,2 위를 했다.

그러면 사람이 직접 고친 글과 결과가 비슷한데, 스킬은 왜 써야 할까?

-> 스킬로 지침과 규약을 제시할 수 있었다.
EX) 스킬 없는 모델은 비유를 지우거나, 원고에 없는 숫자를 지어낸다. - `p99 4.2초에서 0.9초로 줄었습니다`

-> 사내 규칙을 지킬 수 있다.
EX) 우아한형제들은 WordPress 에서 초안을 작성하고, Google Docs 에 올리고 댓글을 다는 형태이다.
검수자가 직접 하던 이 일을, 이제는 LLM 이 자동으로 옮겨 주고 댓글까지 달아 준다.

### AI 냄새 줄이고, 사람 냄새 살리기

> 후반부는 책을 쓰는 관점에서 이야기 한다.

사람들은 아직 AI 를 그렇게 좋아하지 않는다.
같은 소개글도 작성자 표시만 "AI" 로 바꾸면 7점 척도에서 0.81점이 떨어졌다. - AI 편향 현상
(발표에서 소개한 수치이고, 원 자료는 찾지 못했다.)

그렇기에, 글에서 AI 냄새를 줄이고 사람 냄새를 살려야 한다.

### 어떻게 핵심을 적을까

`미션` 장의 의도는

```
강의를 듣고 배우는 시간보다, 직접 문제를 풀고 경험하는 시간을 늘리고 싶었어요.
```

였다. 그대로 쓰면 평소대로 쓰는 글의 수준이라고 말했다.

같은 생각도 어떻게 전할지 방법에 따라, 완전 달라질 수 있다.

- 어원 : 학은 배우는 것, 습은 익히는 것. 우리는 습의 시간을 늘려본다.
- 비유 : 잠수교까지 자전거로 가려는데, 페달이 무겁다면?
- 장면 묘사 : 설명은 끝났는데, 빈 코드 창 앞에서 멈춘다.
- 질문 : 배우는 시간만큼, 그걸 써보는 시간은 있었나요?

현재는 이 중 어원으로 글을 풀어 나가는 걸 선호한다.

> 서구권 기반 학습이 되어있다보니,
> AI가 어원 기반으로 내용을 쓰는 경우는 많이 없어서 사람 냄새가 난다고 말했다.

### 가상의 사람들에게 리뷰를 받아보자


[Nemotron-Personas-Korea](https://huggingface.co/datasets/nvidia/Nemotron-Personas-Korea) 라는 데이터셋이 있다.
이 데이터셋에서 자신의 글을 읽을 페르소나를 추출해서 이 페르소나를 기반으로 내용을 읽게 시켜보자.

> 직접 해보았는데, 클로드한테 이 데이터셋 중 `~~~ 에 어울릴 사람들 추출해줘.` 라고 하면 잘 해준다.

- 대한민국의 실제 인구 통계, 지리, 성격 특성의 분포를 기반으로 합성된 오픈소스 페르소나 데이터셋
- 이름, 성별, 나이, 혼인 상태, 교육 수준, 직업, 거주 지역 등의 속성을 자료를 바탕으로 합성

## 13:50 — 5년의 다국어 숙제, LLM 으로 해결하기

> 한줄 평 : LLM 을 쓰지만 아키텍처는 기존과 다르지 않다. 사람은 기준을 세우고, 일은 AI 가 한다.


> 배민 앱 다국어(일본어, 중국어, 영어)를 LLM 으로 푼 이야기

다국어를 번역하는 건 항상 니즈가 있었다.

- 외국인 관광객들의 손쉬운 사용
- 한국 거주 외국인들의 손쉬운 사용

### 5년 동안 미뤄진 이유

하지만, 현실적인 어려움이 존재했다.

- 정의의 벽 : '두바이 쫀득 쿠키' 를 어떻게 옮기나
- 구축의 벽 : 실시간 번역 파이프라인, 대용량 품질 관리
- 운영의 벽 : 신규, 수정 콘텐츠의 지속 처리

그리고, 배달의 민족 특성상 데이터가 호락호락 하지 않았다. 가게 수십만 개, 메뉴 수천만 개, 약 100GB.
(발표자 말로는 번역가가 직접 작업하면 수백 년이 걸릴 양이라고 한다.)

그 양을 다 처리할 만큼 우선순위가 높지는 않았다.
=> 하지만, LLM 의 성능이 올라가며 PoC 로 진행해볼 만한 가치가 있다고 판단되었다.

### 왜 자바였나

> 2026년 1월 상황

자바는 LLM 서비스에서 사용한 사용자 기반 레퍼런스가 미흡했다.

하지만, LLM 서비스 자체도 모듈화 관점에선 일종의 외부 API 다.
결국 서버 문제로 귀결된다.

- 무상태 추론 -> 조립은 서버의 몫
- SSE(Server-Sent Events) 스트리밍 및 동시 요청 처리
- 자원 제어, 장애 격리

등등 이는 결국 자바에서도 익숙한 영역이다.

2026년 1월 기준으로는 Spring AI 의 기준이 아쉽다고 판단해,
Bedrock SDK 전용 클라이언트 + 모델 무관한 계층으로 구축했다.

### 처음 구조의 문제와 개선

1. 메뉴판 단위 전체를 번역에 요청을 했는데, 아래와 같은 문제가 발생했다.

- 중복 번역
- JSON 파싱 실패로 누락

그래서 메뉴명 단위로 쪼개고, 필드 단위로 변경을 감지했다.

2. 번역을 제대로 못하는 케이스가 존재한다.

- 공기밥 -> Air Rice

잘못된 번역 및 불필요한 번역 요청이 발생하지 않기 위해
번역 사전으로 캐시 조회를 하게 했다.

3. 도메인마다 번역 되는 결과가 달랐다.

- `한 집 배달` 이라는 용어가 있을 때, 각 담당자/도메인 마다 번역체가 다르거나, 결과 불일치

공통 번역 API 를 구축해서 일관되게 관리하고, 표준 사전을 관리했다.
-> 그래도, 수 작업이 필요했다. (글자 하나가 다르거나, 공백이 다르거나 등)

### RAG 기반 도메인 지식 추가

수작업을 없애기 위해 RAG(Retrieval-Augmented Generation, 관련 자료를 찾아 프롬프트에 함께 넣는 방식)를 도입했다.

- 단어를 Vector 화 시켜서 저장을 했다.

> Amazon-Bedrock 의 titan-embed-text 를 사용했다고 함

1. 번역 텍스트 벡터 변환
2. 벡터 사전 조회
3. 번역 요청
	- 벡터 값이 일치하면, 번역 생략
	- 벡터 값이 기준치 아래라면, 같이 전달

벡터화 작업을 하며, 동일한 값이지만 벡터 유사도가 엄청 다른 경우들이 존재

- 10,000 원과 만원의 벡터 유사도는 엄청 다르다.

서버 코드로 먼저 정제한 뒤 요청하게 바꿨다.

### 모델 선택

실제 제품에 적용하며, 비용 문제가 떠오르게 되었다.

 3 가지 모델을 성능 비교 및 검증했다.

- Gemma, Haiku, Qwen

그 중, Gemma 가 종합적으로 점수가 가장 잘 나와서 결정되었다.
추가로, 셀프 호스팅을 할 수 있다는 것도 큰 장점이다.

- 비용 구조
- 확장성
- 데이터 경계
- 지연, 품질 제어

### 최종 번역 시스템 구조

최종 구축한 시스템은 아래와 같다.

> 아래 그림은, 찍은 발표 사진을 기반으로 LLM 에게 정리시킨 그림입니다.

![다국어 번역 시스템 구조](https://assets.youngsu5582.today/obsidian/2026/11/08/2ab61566e2335fcbdbe2ff5728fc59ac.png)

1. 가게 변경, 메뉴 변경 이벤트를 워커가 받는다.
2. 워커는 큐에 메시지를 넣는다.
3. LLM Translator 라는 `번역 LLM 모듈`이 처리를 한다.
4. 다시 워커 큐에 전파한다.
5. 워커 큐는 전시 데이터를 관리하는 Food Data Hub 에 다국어들을 적재한다.

이 아키텍처에서 현재는, 기존 작업 자동화와 프로세스 개선을 해나가고 있다.

#### 다국어 번역 에이전트

예전에는 전시된 문구를 수정하려면

- 문구 추출 -> 다국어 번역 & 엑셀 다운로드 -> 개발자 적용 요청 -> `message.properties` 파일 변환 -> 서버 코드 반영 -> 운영 배포

와 같은 복잡하고, 비효율적인 구조로 되어있다면
이 과정을 자동으로 처리하는 다국어 에이전트를 제공하게 되었다.

#### 자동 검수 기반 번역 품질 강화

위 시스템에서도 문제점들은 존재했다.

- 용어 불일치
- 문구 길이 초과
- UX 가이드 충돌

=> 이를 개선하는 자동 검수 프로세스 도입을 했다.

1. 번역 요청
2. 번역 tool 호출
3. 표준 사전 조회
4. Open LLM 다국어 번역
5. Amazon Bedrock 다국어 검수
6. 검수 기준치 만족 못하면, 슬랙 알림

-> 담당자가 슬랙 확인 후 개선 가능

## 14:50 — 확률적 모델 위에 결정적 시스템

> 한줄 평 : LLM 의 결과가 정형적이지 않더라도, 제어마저 정량적으로 못하는 건 아니다.

> 배민 대화형 검색 에이전트를 구축한 이야기 (자바 + Spring AI 2.0 + Spring Boot 4)

확률적으로 답하는 모델 위에서, 어떻게 결정적 시스템을 세울 것인가.

### 모델 고르기

#### 품질과 성능

품질과 성능의 기준을 세워야 한다.

- 품질 : AI 모델의 응답 정확도
	- 의도 이해
	- 기대 동작
	- 사실 정확도
	- 표현과 정책

- 성능 : 응답속도와 처리량
	- 첫 유의미한 발화
	- 답변 완료
	- 실패율
	- 지연 시간

성능은 기준을 세우기가 쉽다.
하지만, 품질은 모호한 영역이기에 시나리오로 직접 돌려 봐야만 알 수 있다.

#### 비용

외부향 서비스는 이를 고려하지 않으면, 서비스 존속을 할 수 없다!

- 토큰 비용을 건당 비용으로 환산
- 프롬프트 캐싱 적용
	- 앞 부분이 같으면 이전 계산을 다시 써서, 입력 토큰을 더 싸고 빠르게 처리
	- `cache_write` 는 1.2~2배라 잘못 쓰면 더 비싸짐

#### 가용성

AI 서비스는 다른 컴퓨팅 장비에 비해 자주 멈춘다.

발표에서 소개한 공개 수치만 봐도 (원 자료는 찾지 못했다)

- OpenAI API : 99.99%
- ChatGPT : 99.72%
- Claude API : 99.78%

로, 다른 서비스들이 목표로 하는 파이브 나인(99.999%)에 못 미친다.
-> 모델 다중화를 했다.

- 같은 회사 모델끼리는 장애가 날 수 있으므로 다른 계열
- 주간은 GPT, 야간/폴백은 Gemma 4

=> 모델은 고정된 것이 아니다. 서비스에 맞는 기준에 따라 언제든 새 모델을 검토하고 적용할 수 있어야 한다.

- 맥락 데이터 : 유저의 앱 상 이동 경로, 주소지, 최근 주문 내역

### 구조 고르기

LLM 이 앱 내에서 어떻게 일하는지를 구축해야 했다.
LLM 이 작업을 처리하는 방식은 아래와 같다.

#### 작업 처리 방식

흐름을 누가 정하느냐에 따라 네 가지로 나뉜다.

| 유형             | 흐름을 정하는 쪽 | 동작 방식                            | 언제 쓰나                                  |
| -------------- | --------- | -------------------------------- | -------------------------------------- |
| 단일 호출형         | 없음        | 모델을 한 번 호출해 입력을 바로 출력으로 바꾼다      | 입력과 출력 모양이 단순할 때, 판단이 한 번이면 될 때        |
| 워크플로우형 (고정 제어) | 코드        | 코드가 순서를 정하고, 모델은 한 번에 단계 하나만 맡는다 | 할 일이 명확히 정해져 있을 때, 같은 입력에 같은 결과가 필요할 때 |
| 워크플로우형 (동적 제어) | 라우터 LLM   | 라우터 LLM 이 요청마다 실행 경로를 고른다        | 갈래 목록은 정해져 있지만, 자연어로만 어느 갈래인지 알 수 있을 때 |
| 완전 자율형         | 모델        | 모델이 도구를 골라 쓰면서 다음 행동과 종료 시점을 정한다 | 무엇을 할지 미리 정할 수 없을 때<br />(코딩, 리서치, 긴 작업) |

#### trade-off

단일 호출형에서 완전 자율형으로 갈수록 아래 네 가지가 커진다.

| 항목     | 단일 호출형 | 워크플로우형 (고정) | 워크플로우형 (동적) | 완전 자율형 |
| ------ | ------ | ----------- | ----------- | ------ |
| 비용     | 낮음     | ↗           | ↗           | 높음     |
| 지연시간   | 짧음     | ↗           | ↗           | 길음     |
| 기능 복잡성 | 낮음     | ↗           | ↗           | 높음     |
| 추적 어려움 | 쉬움     | ↗           | ↗           | 어려움    |

처음에는 MCP(Model Context Protocol, 모델이 외부 도구를 부르는 규약)를 다 붙인 완전 자율형으로 했지만, 추적 & 비용 & 유지보수가 어려웠다.

- 실행 제어 : 도구 선택과 중간 판단을 코드/로그/메트릭 추적이 어려움
- 응답 시간 : 필요 이상 추론 및 호출 길어지는 요청이 생김
- 비용 : 실행 주권이 AI 에 있으니, 토큰 사용량 & 비용 & 응답 지연이 매번 달라짐
- 검증과 유지보수 : 기능이 늘수록 프롬프트가 커지고, 문제 단계를 찾아 그 부분만 고치기 어려움

=> 워크플로우 형으로 바꿨다.

#### 에이전트 흐름

> 아래 그림은, 찍은 발표 사진을 기반으로 LLM 에게 정리시킨 그림입니다.

![검색 에이전트 흐름](https://assets.youngsu5582.today/obsidian/2026/11/08/3b18dace517bcb839b41804633538ad1.png)

정의된 기능을 정해진 절차로 수행한다. 아래와 같은 장점을 가진다.

- 정해진 시간과 조건 내 일관성 있는 답변
- 여러 사람이 유지보수할 수 있는 가시적인 시스템

유저의 대화가 들어오면 1턴이 시작된다.

1. 의도 분류

`User Context` 에서 `단기 컨텍스트`, `맥락 컨텍스트`, `장기 컨텍스트` 를 수집한다.
이 컨텍스트들을 기반으로 의도 분류(시스템 번역)를 한다.

예를 들어 "만원 이하 국밥 배달 빠른 순으로" 라는 요청이 오면, 의도 분류 LLM 이 이를 `search(keyword="국밥", …)` 처럼 정해진 카테고리로만 바꾼다(시스템 번역).

2. 도메인 분류

도메인 분류는 좀 더 조건을 기반으로 고급지게 분류한다.
어떤 가게를 시킬지라든가, 메뉴를 선택한다든가.

3. 핸들러 실행

의도에서 나온 카테고리와 카테고리에서 나온 결과들을 기반으로 핸들러를 실행한다.

- 특정 의도에 따라 정해진 Handler 만 수행
- 내부 구현 API 호출, DB 호출, MCP 호출 등 구현체에 따라 자유롭게 달라짐
- Validation, 재시도 정책 등도 구현체에 따라 자유롭게 달라짐

> 아래 그림은, 찍은 발표 사진을 기반으로 LLM 에게 정리시킨 그림입니다.

![핸들러 실행](https://assets.youngsu5582.today/obsidian/2026/11/08/90193895c8e0d32b35941bc7e7b3e492.png)

이 흐름으로 아래를 얻었다.

- 분해 : Step 단위 책임을 캡슐화
- 계측 추적 : Step 별 토큰 및 지연 추적 가능
- 최적화 : Step 별 프롬프트 최적화 및 테스트
- 디버깅 : 어느 단계에서 실패했는지 분석해 빠른 디버깅
- 부분 수정 : 단위별 수정 및 배포

여기까지가 희망편이고, 아래는 실제로 풀어야 했던 문제들이다.

### 트러블슈팅

설계대로 흘러가지 않은 순간들도 존재했다.

#### 프롬프트 모방

LLM 이 응답해준 프롬프트 지시문 단어가 그대로 화면 버튼으로 렌더링됐다.

- 결과 머리말 이름이 -> `확인된 갈래는 삼겹살이에요`

화면에 나와도 괜찮은지를 고려해야 한다.

#### 부정 프롬프트

하지 못하는 걸 하지 않게 방지하려고 부정 프롬프트를 설정하니, 의도와 다르게 거절한다.

- `앱 화면 경로 안내 금지` 프롬프트 설정 -> `주문내역 어디서 봐?` 도 거절

부정 프롬프트보다 가능한 것들을 알려주게 변경했다.

#### 할 수 없는걸 거절하기

할 수 없는 기능은 애초에 못하게 방지한다.

- 닫는다는 기능은 처음부터 없다 -> 자기가 할 수 있다고 가정하고, 계속 시도

최대 실패 횟수를 기반으로 처리가 되게 했다.

#### 검색 그만할게요

이제 검색을 그만하겠다고 했는데, 그걸 못 그만두게 했다.

- 할 수 없는걸 거절하게 했다. -> 검색 그만둔다는 건 할 수 없다고 거절

지침과 전처리로 해결한다.

### 에이전트 테스트

원래 전통적 테스트 피라미드는 `단위 -> 통합 -> E2E` 였다.
이는, '입력이 같으면, 출력이 같다' 를 전제로 했다.

-> LLM 은 같은 입력에도 다른 출력이 나와서 assert 로 검증할 수 없고, 테스트 케이스(TC)의 가짓수도 무한대에 가깝다.

=> 하한을 정해서 검증했다.

- LLM-as-Judge : 모델 하나가 기준표로 채점
- LLM-as-Jury : 여러 개 대형 언어 모델이 투표
- Calibration : AI 모델이 출력하는 확신도가 실제 정답인지 확인하고 조정

### 마무리

모델을 결정적으로 만들지 않고, 만들 수도 없다.
우리가 만드는 건 모델의 하한을 지킬 수 있게 설계 하는 것이다.

- 순서는 워크플로우 기반 코드가 정한다
- 테스트로 고칠 때마다 변경선과 하한을 확인한다
- 고객 지표를 기반으로 개선한다. 진짜 품질만은 유저가 알려주기 때문이다.
	- 발화 감정 분석
	- 주문 전환율
	- 세션 전환율
	- 이탈 시간

## 느낀점

이 밖에도 팀 단위 AI 전파, QA, 데이터 분석 등 여러 영역에서 AI 를 쓴 경험을 들었다.

### 아직 정해지지 않은 AI 쓰는 법

팀마다 AI 를 사용하는 방법, AI 를 코드와 서비스에 적용하는 방법, 기준 등은 모두 달랐다.

예를 들어,

- 특정 팀은 '호출하는', '호출되는' 서비스들의 코드 조회 권한을 받아서, 이 흐름을 연결하는 그래프와 변경을 감지하는 시스템
- QA 팀은 의도와 코드가 어긋나지 않게 코드를 기반으로 파싱 -> 매트릭스화 (참고 사진)

![QA 팀의 코드 파싱 매트릭스](https://assets.youngsu5582.today/obsidian/2026/11/08/8587ef57ba6b89d904b5624044409b4f.png)

- 서비스를 구현할 때도 AWS Bedrock Client 기반 자체 구현 / Spring AI 로 기능 구현

LLM 은 상용화된 지 얼마 안 됐다.

기존 금융 · 유통 서비스는 수십 년에 걸쳐 전산화되었다.

- 1970년대 후반 온라인 시스템 -> 1999년 인터넷뱅킹
- 1996년 국내 최초 온라인 쇼핑몰 인터파크

하지만 LLM 서비스는 2022년 11월 ChatGPT 가 나온 뒤로 이제 4년 정도가 되었다.
아직 격동기이고, 앞으로 어떻게 될지 아무도 모른다.

### 그래도 같은 방향

이번 발표들을 들으며 찾은 공통점이 있다.

1. LLM 의 응답을 그대로 믿지 않는다
2. LLM 요청과 응답도 하나의 모듈로 관리한다

LLM 에 단순 `요청 - 응답`하는 게 아니라 정제하거나 제어할 수 있는 방법들을 고민했다.

- 글쓰기에서는 정규식으로 후보 제공
- 코드 -> 구문 트리로 파싱 후 요청
- LLM 요청과 응답을 모듈화해서 외부 API 처럼 관리
- LLM 작업을 자율형이 아닌 워크플로우 형으로 의도적 제어

결국, 제어할 수 없는 것에 의존하지 말자는 향로님의 말이 생각이 났다.

![우아한테크세미나 개발자 원칙 발표 장면](https://assets.youngsu5582.today/obsidian/2026/11/08/5a125e14347e475892d677d29bb84e50.png)

[우아한테크세미나 - 테크 리더 3인이 말하는 "개발자 원칙"](https://www.youtube.com/watch?v=DJCmvzhFVOI)

- LLM 을 믿을 수 있는가?
-> 불가능하다.

LLM 의 응답을 무조건 믿는 게 아니라 `점수 기반 신뢰 / 알림` 기반으로 처리를 한다.
정할 수 없다면, 정보를 종합해서 사용자에게 전달해주는 형식으로 판단을 거친다.

- LLM 결과를 항상 원하는 대로 받을 수 있는가?
-> 불가능하다.
LLM 에게 보낼 요청을 제어하거나(구문 트리 파싱), LLM 에게 받은 응답을(JSON 검사, 모듈화) 제어한다.

무엇을 믿고 무엇을 제어할지 명확하게 판단하고 고민하는 것부터가, LLM 을 써 가는 우리의 자세 아닐까.

### 다양한 시도를 하자

아직 정답은 정해지지 않았다.
설령 정답이 있더라도, 계속 바뀌는 모델 앞에서 그 정답을 확신할 수는 없다.

그래도 해 보지 않으면 모르는 것들이 있다.

- 테크니컬 라이팅에서 LLM 은 아직 어원으로 문장을 풀지 않는다든지 (앞의 10:50 세션)

- 할 수 없는 일은 거절하라고 했더니, 검색 에이전트가 `검색 그만할게요` 까지 거절한다든지 (앞의 14:50 세션)

매번 쓰던 형태를 반복하는 게 아니라, 여러 도메인과 업무에 직접 붙여 보며 LLM 을 대하는 나만의 기준을 쌓아 나가자.
