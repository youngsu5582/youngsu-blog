### 낙관적 락

`int version` 과 같은 칼럼과 `where version = ?` 를 통해
값이 변경되지 않은 상태라고 확인 후, 상태가 변경되었으면 예외를 발생시켜 처리하게 한다.

- 예외는 `javax.persistence.OptimisticLockException` 를 발생시킨다.

### 낙관적 락의 자동 재시도

그러면, 이 예외는 어떨 때 재시도를 시켜도 되는지/안되는지 구분할까?
기준은 재요청이 사용자의 원래 의도를 유지하는가? 이다.

예를 들어,

- 재고 3개 구매 -> 최신 재고 확인 후 여전히 구매 가능하면 재시도

에서 사용자는 재고와 상관없이 3개 구매한 게 수행이 되길 원한다.

- 사용자가 가격 10,000원을 보고 12,000원으로 변경 + 다른 사용자가 15,000원으로 변경

다른 사용자가 15,000 원으로 변경한 시점에서 사용자가 본 10,000 원은 예전의 데이터고 변경된 15,000원을 본다면 행동에 영향을 받을 수 있다.

### 재시도 폭풍 - Retry Storm

재시도를 무조건 해선 안된다.

100 개의 요청이 모두 동일한 데이터를 수정하려고 할 때, 모든 요청이 즉시 재시도하면 다시 충돌할 가능성이 매우 높다.

특히, 낙관적 락은 트랜잭션을 전부 롤백 시키므로
다시 DB 조회 & 처리를 해야하므로 꽤나 부담이 큰 작업이다.

-> 재시도가 추가적인 부하와 충돌을 일으키는 현상이 Retry Storm

이를 방지하기 위해선 아래 요소들을 고려해야 한다.

- 최대 재시도 횟수 제한 : 최초 요청 포함 n회 시도를 제한. 애플리케이션 단 자동 재시도가 아닌, 사용자가 인지할 수 있게 반환 해 재시도 및 다른 처리할 수 있게 한다.
- Exponential Backoff : 충돌이 반복될수록 간격을 지수적으로 증가시킨다. 각 요청이 간격을 다르게 처리되어 요청당 부하가 분산될 수 있다.
- Jitter : 재시도 간격에 무작위 지연 추가해 요청 자체가 동시에 몰리는 걸 방지한다. Backoff 만 적용하면, 요청 100개가 동시에 들어오면 여러 요청도 동일한 간격으로 증가해서 요청을 한다. 이를 분산하기 위해 무작위성을 추가한다.

최종적으로는, 이런 상황이 나온다면 다른 개선을 고려해볼만한다.

낙관적 락은 충돌이 많이 없는 경우를 고려해서 사용해야한다.

- 비관적 락 : 충돌 가능성이 높으면, 락을 획득해 순차적 처리
- 원자적 UPDATE : 단순 차감 및 갱신 시, 조건부 UPDATE 를 통해 조회 & 변경을 하나의 SQL 로 처리
- 요청 직렬화 : 특정 데이터에 요청이 집중된다면, 큐 등을 이용해 순차적 처리 고려

=> 언제나, 이 4개는 Set 로 trade-off 를 고려해보자.
