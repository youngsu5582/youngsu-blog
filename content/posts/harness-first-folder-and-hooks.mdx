## 간결한 CLAUDE.md

처음엔 다들 그렇듯 `CLAUDE.md` 에 간결하고 명확한 규칙을 적었다. 규칙 문서를 다 합쳐도 182줄이었다.

- "브랜치 바꾸지 말고 worktree 써라"
- "커밋 메시지는 티켓 번호로 시작해라"

일하는 방식도 적었다.

- "불명확한 지시나 잘못된 가정은 바로 짚어라"

잘 지킬까? -> 대체로 지킨다.

그런데 작업이 길어지면 일하는 방식에 대한 규칙이 슬그머니 빠졌다.
묻지 않고 짐작으로 진행하거나, 고치기로 한 범위 밖까지 손을 댔다.

## 이대로 괜찮은가?

하지만, 규칙은 여전히 새었다.
작업 자체도 관리되지 않았다. 무엇을 정했는지는 대화에만 남았고, 어디까지 고쳤는지는 대조할 데가 없었다.

-> 710줄이나 적어 뒀는데 왜 이럴까? 하네스가 제대로 돌고 있는 건가? 🤔

3개월 정도 지나고, 하네스가 실제로 어떻게 쓰이고 있는지 실측을 했다.
재 보니 셋 다 의도대로 안 돌고 있었다.

### 규칙

- 규칙 준수율을 재려던 대시보드는 정비한 그날 하루 돌고 끝났다
- 고치려고 만든 스킬(`harness-tune`)은 한 번도 쓰이지 않았다
- API 서버, 프론트 코드, 컨슈머 등 규칙이 모두 혼재되어 있어서 들어오게 된다.

-> 710줄이 지켜지는지 아닌지, 볼 데가 없었다.

> 위 6개 파일이 매 세션 통째로 읽혔다. API 만 고치는 세션에도 프론트 61줄 · 컨슈머 164줄이 같이 들어왔다.

### 스킬

- Obsidian vault 를 옮긴 뒤로, 옛 vault 경로를 보던 스킬 27개가 조용히 멈춰 있었다
- 매일 밤 돌던 정리 스킬(`nightly`)은 5번 정도만 돌고 끊겨있었다

### hook

- 기존 hook 8개는 입력을 환경변수로 받는다고 전제했다.
	- 그런데 Claude Code 는 stdin JSON 으로 넘긴다
	- 전부 첫 가드에서 조용히 `exit 0`

```bash
#!/bin/bash
# checkout-guard.sh — git checkout/switch 사용 시 워크트리 권장 안내
# critical.md 룰: 다른 브랜치 작업 시 worktree 사용 필수.
#
# 동작: stderr로 경고만 출력 (차단 X). 사용자가 의도적으로 사용 가능.
# Hook으로 차단하면 정당한 use case (파일 단위 checkout) 막아서 비실용적.

CMD="${CLAUDE_BASH_COMMAND:-${OPENCODE_BASH_COMMAND:-}}"
[[ -z "$CMD" ]] && exit 0

# 파일 단위 checkout (e.g. git checkout -- path/to/file) 은 제외
if echo "$CMD" | grep -qE "git (checkout|switch)\s+(-\s|--\s|-\-\s|\.\.|\-|--)" ; then
    exit 0
fi

# branch 전환 패턴: git checkout <branch> 또는 git switch <branch>
if echo "$CMD" | grep -qE "^\s*git (checkout|switch)\s+([a-zA-Z0-9._/-]+)\s*$"; then
    BRANCH=$(echo "$CMD" | sed -E 's/.*git (checkout|switch) ([a-zA-Z0-9._\/-]+).*/\2/')
    echo "" >&2
    echo "⚠️  critical.md: 다른 브랜치는 워크트리 사용 권장" >&2
    echo "   git worktree add /tmp/wt-$(echo "$BRANCH" | tr '/' '-') $BRANCH" >&2
    echo "" >&2
    # 차단 안 함 (warning only)
fi

exit 0
```

(예전의 hook 코드)

### 상태 불일치

문서와 허용한 권한도 일치하지 않았다.

| 문서에 적은 것                 | 실제 권한                                       |
| ------------------------ | ------------------------------------------- |
| GitHub 쓰기는 묻고 해라         | `gh pr edit` 자동 허용                          |
| worktree 를 써라, 브랜치 전환 금지 | `git` 전체 자동 허용. 지켜보던 hook 은 경고만 하고 `exit 0` |
| `curl` · `wget` 쓰지 마라    | 둘 다 전체 허용                                   |

```sh
// .claude/settings.local.json — 묻지 않고 실행되는 목록
"Bash(gh pr edit:*)",    // 문서: GitHub 쓰기는 묻고 해라
"Bash(git:*)",           // 문서: 브랜치 전환 금지
"Bash(gh workflow:*)",   // 배포 스킬은 네 번 묻는데, 이 명령을 직접 치면 아무것도 안 묻는다
```

-> 있다고 믿었던 안전장치가, 실제로는 하나도 동작하지 않고 있었다.

## 깨달은 것

문제는 셋이었다.

1. 강제가 안 된다 → 컨텍스트는 아무리 잘 적고 길게 적어도, Claude 가 읽고 따를지 판단한다
2. 쓰이는지 알 수 없다 → 스킬이 불리긴 하는지, hook 이 막긴 하는지 볼 데가 없다
3. 작업이 어떻게 진행되는지 제어할 수 없다 → 무엇을 정했는지는 대화에만 남고, 어디까지 고쳤는지 대조할 데가 없다

> 3번은 2편에서 다룬다. 이 글은 1 · 2번 이야기다.

그렇다고 전부 막을 수는 없었다. 오타 하나에 명세를 쓰라고 하면?
-> 하네스가 작업보다 무거워지고, 결국 우회하게 된다.
=> AI 가 잘하는 건 맡기고, 잊으면 안 되는 것만 코드로 강제하는걸 목표로 했다.

### 폴더 구조 개선

710줄이 문제였던 건 길어서만이 아니었다. 무엇이든 매 세션 통째로 읽혔다.
=> 그래서 먼저 "언제 읽히나" 로 나눴다.

| 언제 읽히나 | 무엇 | 자리 |
|---|---|---|
| 매 세션 | 절대 규칙만. 200줄 상한 | `.claude/rules/` |
| 그 작업을 할 때 | 백엔드 · 컨슈머 · 프론트 코드 규칙 | `.claude/skills/` |
| 그 기능에 처음 손댈 때 | 기능별 요약 · 흐름 · 운영 문서. hook 이 경로를 한 번 알려 준다 | `.harness/domain/<기능>/` |
| 막혔을 때 · 절차가 필요할 때 | 작업 루프 · 위험 등급 · 관례 · 증상 요령의 정본 | `.harness/handbook/how/` |

폴더는 이렇게 생겼다.

```
{repo}/
├── CLAUDE.md                  프로젝트 개요
├── .claude/
│   ├── rules/                 매 세션 읽히는 규칙 (200줄 상한)
│   ├── skills/ · agents/      그 작업을 할 때 읽히는 절차 · 리뷰용 서브에이전트
│   ├── hooks/                 막는 것 · 알려 주는 것
│   └── plans/<날짜-주제>/     작업마다 task.yaml + INDEX.md
├── .harness/
│   ├── handbook/how/          작업 루프 · 위험 등급 · 관례 · 증상 요령
│   ├── domain/<기능>/         그 기능에 처음 손댈 때 읽히는 문서
│   └── private/               검증 기록 · 승인 장부 · 자가 점검 제안
└── scripts/harness/           verify · status · 자가 테스트
```

> claude 의 rules, skills, agents 는 큰 특이점이 없으므로 설명을 생략한다.
### handbook — 규칙의 

처음엔 같은 규칙이 여러 곳에 흩어져 있었다.
승인 받는 문구는 스킬 28개에 따로 적혀 있었고, 가이드 문서는 이미 폐기한 스킬을 여전히 권장 순서로 안내하고 있었다.
-> 한 곳에 두고, 스킬 · hook · CLAUDE.md 는 그 파일을 가리키게 했다.

```
.harness/handbook/how/
├── work-loop.md            작업 루프 — 명세 → 구현 → 검증 → 마무리
├── risk-and-approval.md    위험 등급과 승인
├── guarded-paths.txt       명세 없이는 못 고치는 경로
├── conventions/            코드 관례 실측 결과
└── troubleshooting.md      증상 → 원인 → 할 일 (증상 요령의 원본)
```

위험 등급 문서(`risk-and-approval.md`)에 "묻고 해라 · 하지 마라" 로 적은 명령이
실제 권한 설정에서도 그대로인지는 `permission-audit.sh` 가 확인한다. 앞의 「상태 불일치」 표가 이게 어긋난 모습이었다.

Claude Code 권한 설정에는 목록이 셋 있다. 묻지 않고 실행(allow) · 실행 전에 묻기(ask) · 막기(deny).
프롬프트에서 "항상 허용" 을 누르면 그 명령이 allow 로 옮겨 가는데, 무엇이 옮겨 갔는지는 아무도 보지 않는다.

스크립트는 세 가지를 본다.

- 머지 · PR 생성 · 배포처럼 묻거나 막아야 하는 명령이 allow 에 들어갔다 → 실패
- 막아 둔 명령(머지 · PR 닫기 · 볼륨 삭제)이 deny 에서 빠졌다 → 실패
- allow 가 지난번에 확인해 둔 목록(기준선)보다 늘었다 → 경고, 새로 들어온 명령을 보여 준다

검증 스크립트 안에서 한 번, 턴이 끝날 때 한 번 돈다. 실패하면 어느 줄을 ask · deny 로 되돌리라고 알려 준다.

### domain — 기능마다 문서 한 묶음

- 정책과 명세를 계속해서 추가하며 관리해나간다
- 그 기능 코드에 처음 손대면, hook 이 이 폴더 경로를 한 번 알려 준다

```
.harness/domain/preset/
├── README.md        요약 · 관계 · 결정 · 모르는 것
├── spec.md          정책
├── flow.md          흐름 (mermaid)
├── operations.md    관련해서 발생하는 예외 및 트러블슈팅 기록
└── code-map.md      코드 위치 (스크립트가 만든다)
```

그래도 잊으면 안 되는 건 문서로 남겨 두지 않았다. hook 에 정리해두었다.

## Hook 을 통한 방지

[Mod 글](https://www.youngsu5582.today/posts/claude-code-mod-tool-control)에서 정리했던 것처럼, 사용자가 손댈 수 있는 곳은 두 종류다.

- `CLAUDE.md` · Skill : 프롬프트에 들어가는 글. Claude 가 읽고 따를지 판단한다
-> 잊거나 다르게 해석할 수 있다

- Hook : Claude Code 가 정해진 시점에 실행하는 코드. Claude 판단과 무관하다
-> 강제할 수 있다

EX) `"브랜치 바꾸지 마라"` 라는 걸 하고 싶다면?

- `CLAUDE.md` : Claude 가 컨텍스트로 기억하고 있을 때만 지킨다
- Hook : Claude 가 잊어도 `git checkout feature/...` 가 실행되기 전에 막는다

한 세션 안에서 hook 이 도는 자리는 이렇다.

![한 세션 안에서 hook 이 도는 자리 — 세션 시작 · 도구 호출 앞뒤 · 턴 끝](https://assets.youngsu5582.today/obsidian/2026/11/22/3d597390de21c0c759f1a7ac40482d1e.png)

막는 방법은 단순하다.

도구를 실행하기 전에 hook 이 stdin 으로 JSON 을 받고, exit 2 로 끝나면 그 도구는 실행되지 않는다.
hook 이 stderr 에 쓴 글은 Claude 에게 그대로 전달된다.

-> Claude 가 읽고 다른 방법을 찾는다.

```bash
# 모든 hook 이 공유하는 함수 (.claude/hooks/_lib.sh)
hook_block() {
  echo "$1" >&2   # Claude 에게 전달되는 차단 이유
  exit 2          # 도구 실행을 막는다
}
```

> hook 이 stdin 으로 받는 JSON 은 이렇게 생겼다.

```json
{
  "session_id": "21f9eab7-…",
  "cwd": "/…/proj-680-ci-oom-investigation",
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": { "command": "git checkout develop" }
}
```

지금 막는 것은 다음과 같다.

| hook               | 막는 것                          |
| ------------------ | ----------------------------- |
| `guard-worktree`   | 브랜치 전환 (`git checkout <브랜치>`) |
| `check-commit-msg` | 규약에 안 맞는 커밋 메시지               |
| `guard-scope`      | 자동생성물 · 이미 적용된 마이그레이션 수정      |
| `guard-secret`     | 키 · 토큰을 파일에 쓰기                |

| `guard-approval`   | 승인 줄을 AI 가 쓰기                 |

처음 `CLAUDE.md` 에 적었던 세 줄(브랜치 · 커밋 메시지 · 자동생성 파일)이 hook 으로 옮겼다.

### 예전 hook 과 무엇이 다른가!

`_lib.sh` 와 같이 공통적으로 필요한 로직들은 담았다.
파일마다 전처리/후처리 로직이 존재하면, 관리가 어려워진다.

라이브러리 개념으로 하나의 sh 에서 공통 로직을 관리한다.

```sh
#!/usr/bin/env bash
# _lib.sh

# hook_block <메시지>
# — 도구 실행을 차단한다.
# Claude Code 는 PreToolUse hook 의 exit 2 를 차단으로 해석하고 stderr 를 모델에 전달
hook_block() {
  echo "$1" >&2
  exit 2
}

# hook_trace <hook이름> <판정> <상세>  — 끝 칸 agent= 는 Claude·Codex 구분용
# session= · wt= 는 입력에 있을 때만 붙인다 — 어느 대화 · 어느 워크트리의 판정인지
hook_trace() {
  local extra=""
  
  [ -n "${HOOK_SESSION_ID:-}" ] && extra="${extra}"$'\t'"session=${HOOK_SESSION_ID}"
  [ -n "${HOOK_CWD:-}" ] && extra="${extra}"$'\t'"wt=${HOOK_CWD##*/}"
  
  printf '%s\t%s\t%s\t%s\tstdin=%s\tagent=%s%s\n' \
    "$(date +%FT%T)" "$1" "$2" "${3:-}" \
    "$([ -n "$_HOOK_INPUT" ] && echo yes || echo no)" "${HOOK_AGENT:-claude}" "$extra" >> "$HOOK_TRACE" 2>/dev/null || true
}

# Bash 명령. 배열로 오면 `["bash","-lc","<스크립트>"]` 는 스크립트만, 그 밖은 공백으로 잇는다  
#   (통째로 이으면 git 이 명령 위치에 안 와서 _scan-branch-switch.pl 이 놓친다 — selftest 로 확인)  
hook_command() {  
  hook_field '.tool_input.command | if type=="array" then  
      (if length >= 3 and (.[0] | test("(^|/)(ba|z)?sh$")) and (.[-2] | test("^-[a-z]*c$")) then .[-1] else join(" ") end)    else . end' CLAUDE_BASH_COMMAND  
}

# hook_field <jq경로> <환경변수명>  — stdin JSON 우선, 환경변수 fallback
hook_field() {  
  local jqpath="$1" envname="$2" v=""  
  if [ -n "$_HOOK_INPUT" ] && command -v jq >/dev/null 2>&1; then  
    v="$(printf '%s' "$_HOOK_INPUT" | jq -r "$jqpath // empty" 2>/dev/null || true)"  
  fi  
  [ -z "$v" ] && v="$(eval "printf '%s' \"\${$envname:-}\"")"  
  printf '%s' "$v"  
}

```

- `hook_block` : 도구 실행을 차단하고, 메시지 전달
- `hook_trace` : 판정마다 한 줄 기록
	- 언제 · 어느 hook · 판정 · 입력이 왔나 · Claude/Codex · 어느 대화 · 어느 워크트리 등등
- `hook_command` : 명령어 추출

```bash
#!/usr/bin/env bash
source "$(dirname "$0")/_lib.sh"

CMD="$(hook_command)"
[ -z "$CMD" ] && { hook_trace guard-worktree skip "command 없음"; exit 0; }

HIT="$(printf '%s' "$CMD" | perl "$(dirname "$0")/_scan-branch-switch.pl" 2>/dev/null)"

if [ -n "$HIT" ]; then
  hook_trace guard-worktree BLOCK "$HIT"
  hook_block "차단: 브랜치 전환 대신 worktree 를 쓴다 (critical.md §3) — \`$HIT\` …"
fi

hook_trace guard-worktree pass ""
exit 0
```

1. `hook_command` 를 통해 명령어 수신
2. 브랜치 전환이 발생했는지 확인 — 판정은 `_scan-branch-switch.pl` 이 한다
3. 전환 발생했으면 `hook_block`

### 확인을 위한 기록 남기기

"hook 이 있다" 와 "hook 이 막는다" 는 다르다.
이를 확인하기 위해, 판정할 때마다 입력이 왔는지까지 로그에 남긴다.

```
2026-11-22T16:44:31	guard-worktree	pass		stdin=yes	agent=claude	session=21f9eab7…	wt=proj-680-ci-oom-investigation
2026-11-22T16:44:31	check-commit-msg	skip	commit 아님	stdin=yes	agent=claude	session=21f9eab7…	wt=proj-680-ci-oom-investigation
2026-11-22T16:45:12	guard-worktree	BLOCK	git checkout develop	stdin=yes	agent=claude	session=21f9eab7…	wt=proj-680-ci-oom-investigation
```

hook 의 모든 판정을 한 줄씩 남긴다.

- `stdin=yes` → 입력을 못 받는 일이 다시 생기면 바로 보인다
- `session=` · `wt=` → 잘못 막은 판정이 보이면 그 대화를 바로 연다. 대화 기록 파일 이름이 세션 id 다

### 테스트를 통해 믿고 고치기

hook 은 프로그래밍처럼 정해진 형식대로 검사 및 동작하기 때문에
'이전과 동일하게 도는지', '바뀌어도 문제가 없는지'를 검증해야 한다.

이를 위해 `hook-selftest.sh` 를 만들어서 테스트해서 변경을 부담없이 할 수 있게 만들었다.

케이스 표는 이렇게 생겼다. 막아야 하는 것과 통과시켜야 하는 것을 같이 적는다.

```bash
# hook-selftest.sh — guard-worktree 판정부
scan BLOCK 'git checkout <branch>'          'git checkout develop'
scan BLOCK '앞에 다른 명령이 있어도'          'cd /x && git checkout develop'
scan BLOCK '뒤에 --가 있어도 (구버전 홀)'     'git checkout develop && git log --oneline'
scan BLOCK '환경변수 대입 뒤'                'GIT_TRACE=1 git checkout develop'

scan PASS  '파일 복원 (-- path)'             'git checkout -- module-api/src/main/java/Foo.java'
scan PASS  '새 브랜치 생성 (-b)'              'git checkout -b feature/PROJ-999'
scan PASS  '충돌 해결 --ours <파일> (실제 오차단)' 'git checkout --ours module-api/src/main/java/Foo.java'
```

## 컨텍스트 전달

AI 가 잘하는 일에는 막는 대신 정보를 준다.

| 언제 | 알려 주는 것 |
|---|---|
| Java 줄을 방금 썼을 때 | `FQCN` 같은 한 줄 규칙에 걸렸는지 |
| 기능 코드에 처음 손댈 때 | 그 기능의 문서가 어디 있는지 |
| 명령이 알려진 에러로 실패했을 때 | 요령 한 줄 |
| Java 파일을 고쳤을 때 | 그 모듈 컴파일 결과 ( 깨졌을 때만 ) |

넷 다 도구가 실행된 뒤에 도는 hook 으로 전달한다.
막지 않고, 할 말을 `additionalContext` 에 담아 내보내면 Claude Code 가 그 글을 도구 결과 바로 뒤에 붙여 Claude 에게 넘긴다. Claude 는 다음 행동을 고르기 전에 그걸 읽는다.

```bash
# line-gate-notice.sh — 마지막 줄
jq -nc --arg m "$MSG" '{hookSpecificOutput:{hookEventName:"PostToolUse", additionalContext:$m}}'
```

컴파일 확인만 다르다.
깨졌을 때만 exit 2 와 에러 줄을 내보내고, 이미 고친 파일은 그대로 둔 채 에러만 Claude 에게 돌아간다.

```
[요령] rg-dash-r — rg 의 `-r` 은 재귀가 아니라 `--replace` 다.
`-rn` 이면 매치가 `n` 으로 치환돼 출력된다. rg 는 기본이 재귀라 `rg -n` 이면 된다.

[요령] flyway-unverified — 테스트는 `flyway.enabled: false` + `ddl-auto: create` 이고 workflow 에도 flyway 가 없다.
dev 배포가 첫 실행이니, 빈 DB 에 flyway docker 로 전량 적용해 확인한다.
```

한 줄 규칙은 편집할 때는 알리기만 하고, `verify.sh` 에서 FAIL 로 잡는다.

```python
# scripts/harness/lint/line_gates.py
FQCN = re.compile(r"(?<![\w.@])(?:java|javax|jakarta|lombok|org\.springframework|org\.hibernate|com\.example)\.(?:[a-z]\w*\.)*[A-Z]\w*")
RULES = [
    ("FQCN", "fail", lambda p: p.endswith(".java"),
     lambda c, l: FQCN.search(c),
     "FQCN 인라인 금지 — import 후 단순 이름 (같은 이름 충돌만 예외) · critical.md §1"),
    # …
```

=> `FQCN` 처럼 한 줄로 가릴 수 있는 팀 컨벤션은, 문서가 아니라 검사로 잡는다.

## 마무리

구조는 생각보다 단순했다.

규칙은 문서에 있고 -> 그중 코드로 판정할 수 있는 건 hook 이 막고 -> 검증 결과와 결정은 파일로 남는다.
복잡해 보였던 건 파일마다 달린 `왜` 였다. 그리고 그 `왜` 는 대부분 지시가 지켜지지 않은 날짜와 사례였다.

AI 와 하네스를 만들면서 제일 쓸모 있었던 질문은 이거였다.

> "이 지시가 한 번 실패했다면, 다음엔 뭐가 막아 주지?", "어떻게 파일을 수정할지, 로직을 작성할지 파악하지?"

답이 hook 이나 스크립트면 옮긴다. 답이 없으면, 그 지시는 아직 문서에 남겨 둔다.
작업을 명세로 붙잡은 이야기는 [[2편 명세로 작업 붙잡기|2편]]에서 이어 간다.
